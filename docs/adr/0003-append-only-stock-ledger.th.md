# ADR-0003: สต๊อกคือบัญชีเคลื่อนไหวแบบเพิ่มได้อย่างเดียว (append-only) ที่เกิดจากเอกสารที่ post แล้ว

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-25
- **English:** [0003-append-only-stock-ledger.md](0003-append-only-stock-ledger.md)

## บริบท

โมเดลสต๊อกที่ง่ายที่สุดคือคอลัมน์ `quantity` ที่บวกเพิ่มและหักลดไปเรื่อยๆ — ซึ่งเป็นสิ่งที่ PaynEat POS ทำสำหรับร้าน
อาหารร้านเดียว แต่ใน ERP โมเดลนี้ตอบคำถามที่สำคัญไม่ได้: ทำไมยอดคงเหลือนี้จึงเป็นเท่านี้ ณ วันที่ในอดีตเรามีของอยู่
เท่าไร สต๊อกนี้มาจากใบรับสินค้าใบไหน และใครเป็นคนเปลี่ยนมัน ทั้งผู้ตรวจสอบบัญชี การ recall และการคิดต้นทุนสิ้นงวด
ล้วนต้องพึ่งคำตอบเหล่านี้

## การตัดสินใจ

1. **การเปลี่ยนแปลงสต๊อกทุกครั้งคือรายการเคลื่อนไหว** รายการหนึ่งบันทึกรายการสินค้า lot สถานที่เก็บสต๊อก จำนวนแบบมี
   เครื่องหมายบวก/ลบในหน่วยหลัก จำนวนหน่วยที่สอง (ถ้ามี; ADR-0005) ต้นทุนต่อหน่วย เอกสารที่ post ผู้ใช้ที่ post
   และเวลาที่ post รายการเคลื่อนไหว**จะไม่ถูกแก้ไขหรือลบเลย**
2. **ยอดคงเหลือเป็นค่าที่คำนวณจากรายการเคลื่อนไหว** ยอดคงเหลือต่อรายการสินค้า lot และสถานที่เก็บสต๊อก คือผลรวมของ
   รายการเคลื่อนไหว อาจมีตาราง snapshot เก็บยอดคงเหลือไว้ (cache) เพื่อความเร็ว ซึ่งสร้างใหม่ได้จากบัญชีเคลื่อนไหว
   และหากข้อมูลไม่ตรงกันเมื่อใด ให้ยึดบัญชีเคลื่อนไหวเป็นหลัก
3. **มีเพียงเอกสารเท่านั้นที่เขียนลงบัญชีเคลื่อนไหวได้** ใบรับสินค้า ใบสั่งผลิต ใบโอน ใบปรับยอด และใบส่งคืนสินค้า เริ่มต้น
   เป็นร่าง ซึ่งแก้ไขได้และไม่มีผลกับสิ่งใด **การ post (ลงรายการ)** จะเขียนรายการเคลื่อนไหวทั้งหมดของเอกสารใน transaction
   เดียว หรือไม่เขียนเลยสักรายการ
4. **เอกสารที่ post แล้วแก้ไขไม่ได้ การแก้ข้อผิดพลาดทำด้วยการกลับรายการ** ความผิดพลาดแก้ได้โดย post เอกสาร
   กลับรายการที่หักล้างเอกสารเดิมได้พอดีทุกประการ แล้วจึง post เอกสารที่ถูกต้อง ทั้งสองฉบับยังคงมองเห็นได้
5. **สต๊อกติดลบได้หรือไม่ขึ้นอยู่กับประเภทสถานที่เก็บสต๊อก**
   - **โรงงาน คลัง ระหว่างขนส่ง: ห้ามติดลบเด็ดขาด** การ post เอกสารที่จะทำให้ lot ใดก็ตามต่ำกว่าศูนย์จะถูกปฏิเสธ
     การเคลื่อนไหวทุกครั้งที่สถานที่เหล่านี้มีเอกสารรองรับ ยอดติดลบจึงหมายถึงข้อผิดพลาดได้อย่างเดียว
   - **สาขา: ติดลบได้ และจะถูกติดธง (flag)** การใช้วัตถุดิบของสาขามาจากการขายที่เกิดขึ้นไปแล้ว ของจริงอยู่ในมือพ่อครัว
     แล้ว ระบบจึงต้องตามความเป็นจริง ยอดคงเหลือติดลบที่สาขาจะขึ้นธงแจ้งให้ทำการตรวจนับสต๊อก
6. **การ post พร้อมกันหลายรายการจะไม่ทำให้ lot ถูกตัดเกินกว่าที่มี** การ post จะล็อกแถวยอดคงเหลือของทุก lot ที่
   เกี่ยวข้อง (`SELECT … FOR UPDATE` ตามลำดับที่คงที่) ก่อนตรวจสอบและเขียน เอกสารสองฉบับจึงไม่สามารถตัดกิโลกรัมสุดท้าย
   ของ lot เดียวกันไปพร้อมกันได้
7. **การปิดงวดทำแยกตามสถานที่เก็บสต๊อก** แต่ละสถานที่มีวันที่ที่ปิดงวดไว้ถึง (closed-until date) การ post ที่ลงวันที่
   ตรงกับหรือก่อนวันนั้นจะถูกปฏิเสธ การเปิดงวดใหม่เป็นการกระทำของ admin ซึ่งตัวมันเองก็ถูกบันทึกไว้เพื่อการตรวจสอบ
   (audit) ด้วย

## ผลที่ตามมา

- ยอดคงเหลือใดๆ ณ วันที่ใดๆ ในอดีตสามารถคำนวณซ้ำได้ และสต๊อกทุกหน่วยย้อนรอยไปถึงเอกสารและบุคคลที่เคลื่อนย้ายมันได้
  — บัญชีเคลื่อนไหวเป็น audit trail ของสต๊อกในตัวเอง
- การแก้ข้อผิดพลาดช้ากว่าการแก้ตัวเลขตรงๆ ซึ่งเป็นความตั้งใจของการออกแบบ
- พื้นที่จัดเก็บเพิ่มขึ้นตามปริมาณกิจกรรม ไม่ใช่ตามจำนวนรายการสินค้า สำหรับเครือร้านอาหารถือว่าไม่มาก และ snapshot
  ช่วยให้การอ่านยังเร็ว
- ตรรกะการ post ต้องเขียนด้วย SQL transaction และการล็อกแถวอย่างชัดแจ้ง ซึ่งจำกัดวิธีใช้ชั้นเข้าถึงข้อมูล
  (data-access layer) สำหรับบัญชีเคลื่อนไหว (ดู ADR เรื่อง backend stack)

## ทางเลือกที่พิจารณา

- **เก็บจำนวนที่แก้ไขค่าได้ต่อรายการสินค้าและสถานที่เก็บสต๊อก** ปฏิเสธด้วยเหตุผลตามหัวข้อบริบท
- **อนุญาตให้สต๊อกติดลบได้ทุกที่** ปฏิเสธ: ที่โรงงาน การติดลบจะซ่อนข้อผิดพลาดในการรับสินค้าและการผลิต แทนที่จะทำให้
  ข้อผิดพลาดปรากฏขึ้นมา
- **ห้ามขายที่สาขาเมื่อสต๊อกเป็นศูนย์** ปฏิเสธ: ระบบที่ไม่ยอมให้ขายอาหารที่พ่อครัวถืออยู่ในมือจะถูกหลีกเลี่ยงไม่ใช้ แล้ว
  ตัวเลขของระบบจะแย่ยิ่งกว่าไร้ประโยชน์
