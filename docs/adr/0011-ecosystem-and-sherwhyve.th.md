# ADR-0011: ระบบนิเวศเดียวกัน — PaynEat POS, PaynEat ERP, Cwork และ SherWhyve

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-25
- **English:** [0011-ecosystem-and-sherwhyve.md](0011-ecosystem-and-sherwhyve.md)

## บริบท

ตอนนี้มีสี่โปรเจกต์ของผู้ดูแลคนเดียวกันที่แตะเชนร้านอาหารเดียวกันจากคนละด้าน:

| โปรเจกต์ | คืออะไร | การเปิดเผย |
|---|---|---|
| [PaynEat POS](https://github.com/SuruchBoss/PaynEat) | ระบบขายหน้าร้านของสาขา ใช้เดี่ยวได้ | Public, Apache 2.0 |
| PaynEat ERP (repo นี้) | ERP ฝั่งซัพพลาย: จัดซื้อ โรงงาน กระจายสินค้า สต๊อก ต้นทุน | Public, Apache 2.0 |
| [Cwork](https://github.com/SuruchBoss/Cwork) | ระบบสารสนเทศ HR: บุคลากร เวลาทำงาน การลา เงินเดือน | Public, Apache 2.0 |
| SherWhyve | AI สืบสวนเหตุขัดข้องสำหรับทีม support และทีมพัฒนา อ่าน log, metric และสถานะของคลัสเตอร์ผ่านการตรวจแบบอ่านอย่างเดียว แล้วตอบเป็นสมมติฐานเรียงลำดับที่มีหลักฐานรองรับ | Private |

ถ้าไม่กำหนดขอบเขตให้ชัด ทั้งสี่จะค่อยๆ ทำงานซ้อนกัน ถ้ากำหนดชัด ทั้งสี่จะประกอบกันเป็นระบบนิเวศเดียว ที่แต่ละ
ระบบทำงานเดียว และระบบอื่นพึ่งพามันได้

## การตัดสินใจ

### 1. แต่ละระบบเป็นเจ้าของโดเมนเดียว และเป็นระบบที่เป็นเจ้าของข้อมูลนั้น

| ข้อมูลหรือหน้าที่ | เจ้าของ |
|---|---|
| ออเดอร์ การชำระเงิน กะ ใบกำกับภาษีที่สาขา | PaynEat POS |
| รายการสินค้า สูตร ซัพพลายเออร์ สถานที่ สต๊อก lot ต้นทุน การวางแผน | PaynEat ERP |
| พนักงาน เวลาทำงาน การลา เงินเดือน ค่าแรงต่อศูนย์ต้นทุน | Cwork |
| การสืบสวนเหตุขัดข้องทางเทคนิคของระบบข้างต้น | SherWhyve |

### 2. ใช้วิธีเชื่อมระบบแบบเดียวกันทั้งระบบนิเวศ

ไม่มีระบบไหนอ่านฐานข้อมูลของระบบอื่น ระบบเชื่อมกันผ่าน API และ event ที่มีเวอร์ชัน ส่งจาก outbox แบบ
transactional พร้อม idempotency key — แบบเดียวกับที่ PaynEat ERP ใช้กับ POS (ADR-0002) และที่ Cwork ใช้อยู่ภายใน
**รหัสสถานที่คือกุญแจร่วม:** สาขาหรือโรงงานหนึ่งแห่งมีรหัสคงที่เดียวกันใน ERP, ใน POS และในฐานะ work location
ของ Cwork

### 3. ทุกระบบต้องสืบสวนได้ (SherWhyve บทบาท A — เริ่มตั้งแต่ทิกเก็ตแรก)

SherWhyve อธิบายได้เฉพาะสิ่งที่ระบบบันทึกไว้ PaynEat ERP จึงถือว่าการสังเกตการณ์ระบบ (observability) เป็นสัญญา
เริ่มตั้งแต่โครงระบบแรก (walking skeleton):

- **log แบบ JSON มีโครงสร้าง** ในทุก request, ทุกการ post และทุก event ของการเชื่อมระบบ โดยมี **correlation id**
  ที่ตามกระแสงานทางธุรกิจหนึ่งเรื่องข้ามระบบได้: idempotency key ของยอดขายหนึ่งรายการ ตั้งแต่ outbox ของ POS
  จนถึงรายการเคลื่อนไหวใน ERP ที่มันสร้าง, เลขที่เอกสารตั้งแต่ร่างจนถึงการ post
- **metric ของสุขภาพการเชื่อมระบบและการ post:** อายุของ event ที่เก่าที่สุดที่ยังส่งไม่ออกจาก outbox, จำนวน event
  ยอดขายที่รับ ซ้ำ และถูกปฏิเสธ, จำนวนการ post ที่พยายามและถูกปฏิเสธ (โดยมีกฎที่ปฏิเสธเป็น label), จำนวนการดึง
  master data ต่อ POS instance
- **ห้ามมีความลับหรือข้อมูลส่วนบุคคล** ใน log หรือใน label ของ metric

คำถามอย่าง *"ยอดขายจากสาขา 2 หยุดเข้า ERP ตั้งแต่บ่ายสองโมง"* จึงตอบได้ด้วยหลักฐานผ่าน SherWhyve connector
ตัวจริงของ SherWhyve รองรับ Google Cloud (Cloud Logging, Cloud Monitoring, Kubernetes) การใช้งานจริงจึงต้องให้ ERP
รันอยู่บนนั้น ที่อื่นสามารถเล่นเคสที่บันทึกไว้ซ้ำผ่าน connector แบบ fixture ของ SherWhyve ได้

### 4. นักวิเคราะห์ธุรกิจของ ERP ใช้วิธีของ SherWhyve ไม่ใช่โค้ดของ SherWhyve (บทบาท B — หลัง v1)

ERP ก็มีเหตุขัดข้องของตัวเอง: yield ตกจาก 70% เหลือ 62%, สาขาหนึ่งใช้ไก่เกินสูตร 12%, ต้นทุนต่อชิ้นพุ่ง, ของมาถึง
ในอุณหภูมิที่อุ่นเกิน หลัง release แรก ERP จะมี **ตัวสืบสวนส่วนต่าง (variance investigator)** ที่สร้างบนหลักการ
ที่ SherWhyve พิสูจน์แล้ว:

- เรียกได้เฉพาะ **การอ่านข้อมูล ERP ที่กำหนดไว้ในระดับ schema** เท่านั้น ดังนั้น "มันเปลี่ยนแปลงอะไรไม่ได้" เป็น
  คุณสมบัติของโค้ด ไม่ใช่คำสั่งใน prompt
- ตอบเป็น **สมมติฐานเรียงลำดับ แต่ละข้ออ้างหลักฐาน** (รายการเคลื่อนไหว, lot, เอกสาร, ผลการตรวจรับ) จาก
  **trace ของการตรวจที่ครบถ้วน**
- **"ข้อมูลไม่พอ และนี่คือสิ่งที่ขาด" เป็นคำตอบที่ถูกต้อง** ไม่มีการนำเสนอการอนุมานว่าเป็นข้อเท็จจริง
- **ประเมินผลกับเคสที่บันทึกไว้** ก่อนปล่อยใช้ โดยมีเกณฑ์ผ่าน/ไม่ผ่าน

AI สำหรับพยากรณ์และจับจังหวะการซื้อที่เลื่อนไว้ใน ADR-0009 จะสร้างบนฐานเดียวกันนี้ รวมถึงกฎ "ตอบผ่าน
tool-calling เท่านั้น" ที่ผู้ช่วย AI ของ PaynEat POS ใช้อยู่แล้ว

**ไม่มีการคัดลอกโค้ดของ SherWhyve มาไว้ใน repo นี้** เพราะ SherWhyve เป็น private ส่วน repo นี้เป็น public ภายใต้
Apache 2.0 การคัดลอกเท่ากับเปิดเผยโค้ดนั้น ข้อนี้จะเปลี่ยนก็ต่อเมื่อ core ของ SherWhyve ถูกเปิดเป็น open source
เอง ซึ่งจะต้องบันทึกเป็น ADR ใหม่

## ผลที่ตามมา

- ทิกเก็ตโครงระบบแรกรวมข้อตกลงเรื่อง log และ metric ไว้ด้วย และทิกเก็ตถัดๆ ไปเพิ่ม metric ของกระแสงานที่ตัวเองสร้าง
  การเติม correlation id เข้าไปในการเชื่อมระบบที่ใช้งานอยู่แล้ว แพงกว่าการเริ่มมีตั้งแต่ต้นมาก
- เอกสารสาธารณะเอ่ยชื่อ SherWhyve และบทบาทของมัน แต่ไม่ใส่ลิงก์ตราบที่ยังเป็น private
- ทั้งสี่โปรเจกต์ประเมินคู่กันได้ในฐานะผลงานชุดเดียวที่สอดคล้องกัน โดยแต่ละตัวยังใช้งานเดี่ยวได้

## ทางเลือกที่พิจารณาแล้ว

- **ฝัง SherWhyve ไว้ใน ERP เป็นนักวิเคราะห์ของมัน** ปฏิเสธ: ผู้ใช้คนละกลุ่ม (ฝ่ายปฏิบัติการและการเงิน ไม่ใช่วิศวกร
  support) หลักฐานคนละแบบ (บัญชีเคลื่อนไหวและเอกสาร ไม่ใช่ log) และจะเป็นการเปิดเผยโค้ด private
- **เพิ่ม observability หลัง release แรก** ปฏิเสธ: กระแสงาน POS → ERP จะออกไปใช้งานโดยไม่มี id ที่ใช้ตามยอดขาย
  หนึ่งรายการได้ตั้งแต่ต้นจนจบ
- **ปล่อยให้แต่ละโปรเจกต์เป็นอิสระโดยไม่กำหนดขอบเขต** ปฏิเสธ: การทับซ้อน (แหล่งข้อมูลพนักงาน สถานที่ หรือค่าแรง
  สองแหล่ง) คือสิ่งที่ ERP มีไว้เพื่อป้องกันโดยเฉพาะ
