# ADR-0012: จุดยืน — ตัวเลือก open source ที่ดีที่สุดในตลาดเฉพาะ ไม่ใช่ ERP ครอบจักรวาล

- **สถานะ:** ยอมรับแล้ว; ส่วน "ไม่มีรุ่นเสียเงิน" ในข้อ 4 ถูกแทนที่โดย [ADR-0015](0015-editions-community-and-enterprise.th.md)
- **วันที่:** 2026-09-25
- **English:** [0012-positioning-niche-depth-over-breadth.md](0012-positioning-niche-depth-over-breadth.md)

## บริบท

เกณฑ์เปรียบเทียบที่คนนึกถึงก่อนสำหรับ ERP แบบ open source คือ Odoo ความกว้างของ Odoo — บัญชี HR CRM การผลิต
ร้านค้าออนไลน์ และอื่นๆ อีกมาก รองรับหลายประเทศ ต่อยอดโดยชุมชนขนาดใหญ่และเครือข่าย partner — เกิดจากเวลาราวสอง
ทศวรรษ บริษัทที่มีทีมพัฒนาขนาดใหญ่ และระบบนิเวศของ module ที่คนอื่นเขียน ไม่ได้เกิดจากโค้ดอย่างเดียว

โปรเจกต์นี้สร้างโดยผู้ดูแลคนเดียวร่วมกับ AI coding agent ถ้าไล่ตามความกว้างแบบนั้น จะได้ module ที่ทำครึ่งๆ
กลางๆ จำนวนมาก ซึ่งคือสิ่งที่ ADR-0001 ปฏิเสธไว้แล้ว เพราะมันทำลายความน่าเชื่อถือในสายตาคนที่โปรเจกต์นี้ต้องการ
ให้ยอมรับ

ความลึกในสนามแคบคือการแข่งขันคนละแบบ ERP ทั่วไปมองธุรกิจอาหารเป็นอุตสาหกรรมหนึ่งในหลายอุตสาหกรรม ความต้องการเฉพาะ
ของอาหาร เช่น รายการน้ำหนักแปรผัน yield กับการปันต้นทุนลงผลิตภัณฑ์ร่วม และการย้อนรอย lot แบบตรงไปตรงมา มักต้อง
ใช้ module เสริมหรือการปรับแต่ง ส่วนเรื่องเฉพาะของไทย — PromptPay ใบกำกับภาษีไทย การขายตามน้ำหนักด้วยตาชั่ง
กฎแรงงานและเงินเดือนของไทย — ยิ่งห่างจากแกนของ ERP ทั่วไปออกไปอีก (ข้อสังเกตเกี่ยวกับ ERP ทั่วไปเหล่านี้ควรตรวจกับ
รุ่นล่าสุดของแต่ละตัวอีกครั้งก่อนนำไปอ้างในที่สาธารณะ)

## การตัดสินใจ

1. **เป้าหมายคือเป็นตัวเลือก open source ที่ดีที่สุดสำหรับเชนร้านอาหารไทยที่คุมห่วงโซ่อุปทานเอง** ไม่ใช่เป็น ERP
   ครอบจักรวาล และไม่ใช่การไล่ให้กว้างเท่า Odoo
2. **แบ่งเป็นสามระดับ และระบุว่าเป้าคือระดับไหน:**

   | ระดับ | หมายถึง | เป็นเป้าไหม |
   |---|---|---|
   | 1. ผลงานอ้างอิงที่น่าเชื่อถือ | เส้นทาง end-to-end ของ release แรกทำงานได้แม่นยำ และคนที่รู้จริงในวงการยอมรับ | ใช่: release แรก |
   | 2. ใช้งานจริงในหลายเชน | release ที่เสถียร การอัปเกรดที่ไม่ทำให้ข้อมูลเสียหาย คู่มือติดตั้งและใช้งาน การแก้ไขที่ขับเคลื่อนด้วยผู้ใช้จริง | **ใช่: นี่คือเป้าหมาย** |
   | 3. แพลตฟอร์มแบบ Odoo | ระบบ module ให้คนอื่นต่อยอด ชุมชนผู้ร่วมพัฒนา partner ที่ติดตั้งให้ลูกค้า | ไม่ใช่: ต้องมีคนอื่นร่วม จะพิจารณาใหม่ต่อเมื่อเกิดชุมชนขึ้นจริง |

3. **เชื่อมต่อแทนการแข่ง** บัญชีแยกประเภทยังอยู่นอกขอบเขต (ADR-0001) ข้อมูลที่ ERP export ต่องวดถูกออกแบบให้นำเข้า
   โปรแกรมบัญชีที่เชนใช้อยู่แล้วได้ — ซึ่งอาจเป็น Odoo เองหรือโปรแกรมบัญชีของไทย — ทำให้ ERP นี้เป็นชิ้นส่วนที่เชน
   เพิ่มเข้าไปได้ ไม่ใช่ระบบที่บังคับให้ย้ายทั้งหมด ส่วนจะรองรับโปรแกรมไหนก่อน ให้ผู้ใช้จริงเป็นคนบอก ไม่เดาเอง
4. **จุดต่างที่ต้องรักษาไว้** คือสิ่งที่ผลิตภัณฑ์ที่เน้นความกว้างไม่ได้ให้ความสำคัญเป็นอันดับแรก: ความลึกด้านอาหาร
   (ADR-0003 ถึง ADR-0007), เปิดทั้งหมดภายใต้ Apache 2.0 โดยไม่มีรุ่นเสียเงิน, ใช้งานแบบไทยเป็นหลักทั้งระบบนิเวศ
   (ADR-0011) และ AI ที่ตอบจากหลักฐานเท่านั้นและบอกตรงๆ เมื่อข้อมูลไม่พอ (ADR-0011)

## ผลที่ตามมา

- คำขอขยายขอบเขตถูกตัดสินด้วยคำถามเดียว: สิ่งนี้รับใช้เชนร้านอาหารไทยที่คุมห่วงโซ่อุปทานเองหรือไม่ คำขอที่อยู่นอก
  นั้น — อุตสาหกรรมอื่น กฎภาษีของประเทศอื่น CRM ทั่วไป — จะถูกปฏิเสธหรือปล่อยให้เป็นเรื่องของการเชื่อมต่อ
- การตั้งเป้าระดับ 2 ทำให้วินัยทางวิศวกรรมบางอย่างเป็นส่วนหนึ่งของขอบเขตตั้งแต่ต้น ไม่ใช่ทีหลัง: release ที่มี
  เลขเวอร์ชันและบันทึกการเปลี่ยนแปลง migration ของฐานข้อมูลที่ทดสอบกับสำเนาข้อมูลของ release ก่อนหน้า เส้นทาง
  อัปเกรดที่มีเอกสาร และคู่มือติดตั้งและใช้งาน
- หลัง release แรก ผู้ใช้จริงเป็นคนกำหนดลำดับความสำคัญ PaynEat POS มีผู้ใช้จริงรายแรกแล้ว ส่วน ERP ควรหาเชนหนึ่ง
  แห่งที่ยินดีทดลองใช้
- การเปรียบเทียบกับ Odoo ทุกครั้งต้องพูดตรงไปตรงมา: แคบกว่า ลึกกว่าในสนามเดียว เปิดทั้งหมด และออกแบบให้อยู่ข้างๆ
  เครื่องมือที่เชนมีอยู่แล้ว

## ทางเลือกที่พิจารณาแล้ว

- **ตั้งเป้าความกว้างระดับ Odoo** ปฏิเสธ: ผู้ดูแลคนเดียวทำไม่ได้ และการพยายามจะบ่อนทำลายความน่าเชื่อถือที่
  โปรเจกต์นี้ตั้งใจสร้าง
- **ทำเป็น module ของ Odoo แทน ERP ที่ยืนได้เอง** ปฏิเสธในตอนนี้: จะผูกโมเดลโดเมนไว้กับโมเดลข้อมูลและรอบ release
  ของผลิตภัณฑ์อื่น และระบบนิเวศ (POS, Cwork, SherWhyve) ถูกสร้างบนระบบที่ยืนได้เองแล้วเชื่อมกันด้วยสัญญา การ export
  ไป Odoo เปิดทางนั้นไว้ได้โดยไม่ต้องพึ่งพา
