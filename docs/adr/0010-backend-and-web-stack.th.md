# ADR-0010: Stack — NestJS, Prisma และการ post บัญชีสต๊อกด้วย SQL ตรง, หน้าจอ React; ใช้แนวเดียวกับ Cwork

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-25
- **English:** [0010-backend-and-web-stack.md](0010-backend-and-web-stack.md)

## บริบท

ในช่วงออกแบบ ตอนแรกเลือก Express กับ query builder ชื่อ Kysely เหตุผลหลักคือ agent คุ้นกับการแบ่ง layer
แบบ Express ของ PaynEat POS อยู่แล้ว และบัญชีเคลื่อนไหวสต๊อกต้องการ SQL, transaction และการล็อกแถวที่
มองเห็นได้ชัด (ADR-0003) ซึ่ง ORM อาจซ่อนไว้

ก่อนเริ่มเขียนโค้ด เมื่อดู [Cwork](https://github.com/SuruchBoss/Cwork) ซึ่งเป็นระบบ HR คู่กันของผู้ดูแล
คนเดียวกันอย่างละเอียด พบว่ามีโครงสร้างตรงกับที่ ERP นี้ต้องการ มากกว่า POS เสียอีก:

- NestJS 11 แบบ modular monolith บน PostgreSQL 16 แต่ละ module เป็นเจ้าของตารางของตัวเอง และ module
  ต่างๆ เรียกใช้กันผ่าน service เท่านั้น ไม่เรียก repository ของกันและกันตรงๆ
- กฎธุรกิจเขียนเป็นฟังก์ชันบริสุทธิ์ในโฟลเดอร์ `domain/` ของแต่ละ module ทดสอบได้โดยไม่ต้องมีฐานข้อมูล
- มี outbox แบบ transactional (`FOR UPDATE SKIP LOCKED`), ตัวล็อกงานตั้งเวลา และ sequence service สำหรับ
  ออกเลขที่เอกสารแบบไม่ขาดช่วง — จุดที่สำคัญเขียนเป็น SQL ตรงผ่าน Prisma ทั้งหมด
- ยืนยันตัวตนด้วย JWT พร้อมการยืนยันหลายขั้นตอน (MFA), guard ตรวจสิทธิ์ และ audit log
- เทสต์ end-to-end ด้วย Jest และ supertest บน PostgreSQL จริง ที่ถูก migrate ล้างข้อมูล และใส่ข้อมูลบริษัท
  demo ก่อนรันทุกครั้ง
- หน้าจอหลังบ้าน React 19 + Vite ที่มีระบบภาษาไทย/อังกฤษของตัวเอง และตรวจ accessibility ในเทสต์

## การตัดสินใจ

1. **โครงสร้าง repo:** `backend/` (API ด้วย NestJS), `web/` (หน้าจอ React), `contracts/` (เอกสาร
   OpenAPI และ JSON schema ของ event ที่มีเวอร์ชัน ใช้ร่วมกับ PaynEat POS ตาม ADR-0002) และ
   `docker-compose.yml` ที่รัน PostgreSQL, API และหน้าจอ
2. **Backend:** NestJS 11 แบบ modular monolith, TypeScript, PostgreSQL 16 ขอบเขตของ module ตาม ADR-0001
   ของ Cwork: module เป็นเจ้าของตารางของตัวเอง module อื่นใช้ผ่าน service ของมัน
3. **ฟังก์ชันโดเมนบริสุทธิ์:** กฎทุกข้อที่ผิดแล้วเสียหายแพง — การเลือก lot แบบ FEFO, การปันต้นทุน, yield,
   การตรวจค่าที่ยอมรับได้, การแยกหน้าที่, คำแนะนำตาม par — อยู่ใน `modules/<name>/domain/` เป็นฟังก์ชัน
   บริสุทธิ์ ไม่แตะฐานข้อมูล framework หรือนาฬิกา เว้นแต่ถูกส่งเข้ามา
4. **การเข้าถึงข้อมูล:** ใช้ Prisma สำหรับ schema, migration และการอ่านเขียนทั่วไป **ยกเว้นบัญชีเคลื่อนไหวสต๊อก:**
   การ post เอกสารและการล็อกยอดคงเหลือของ lot ทำโดย module ledger เท่านั้น ด้วย SQL ตรงเท่านั้น ภายใน
   transaction เดียว โดยล็อกแถวยอดคงเหลือตามลำดับที่คงที่ ไม่มี module อื่นเขียนตาราง ledger หรือตาราง
   ยอดคงเหลือ ไม่ว่าจะผ่าน Prisma หรือวิธีใดก็ตาม
5. **หน้าจอหลังบ้าน:** React 19, Vite, TanStack Query, React Router, zod รองรับไทยและอังกฤษตั้งแต่หน้าจอแรก
   ตามแนวทาง i18n ของ Cwork ทดสอบด้วย Vitest กับ Testing Library และ axe สำหรับ accessibility
6. **เทสต์:** Jest unit test สำหรับฟังก์ชันโดเมน และ Jest + supertest end-to-end ที่เรียก HTTP API จริง
   บน PostgreSQL จริง ซึ่งถูก migrate ล้างข้อมูล และใส่ข้อมูลเชนไก่ทอด demo ก่อนรัน ชุดเทสต์ end-to-end นี้
   คือสิ่งที่นิยาม "เสร็จ" ใน `CLAUDE.md` หมายถึง
7. **นำโค้ดจาก Cwork มาใช้ด้วยการคัดลอกพร้อมบันทึกที่มา ไม่ใช่ทำเป็น package ร่วม:** การตั้งค่าและตรวจ
   environment, การจัดการ error, Prisma service, outbox, guard และ decorator ตรวจสิทธิ์, sequence service,
   การยืนยันตัวตนพร้อม MFA, module audit, ตัวล็อกงาน และโครงหน้าจอหลังบ้าน (layout, i18n, API client,
   route guard) ถูกคัดลอกมาปรับใช้ บทบาทเปลี่ยนเป็น 7 บทบาทของ ERP (ADR-0008) และ `NOTICE` บันทึกที่มาไว้
8. **ตรวจสถาปัตยกรรมใน CI:** สคริปต์ในแนวเดียวกับตัวตรวจ layer ของ PaynEat POS จะทำให้ build ล้มเมื่อ
   โฟลเดอร์ `domain/` import framework หรือ Prisma, เมื่อ module หนึ่ง import ส่วนภายในของอีก module แทนที่จะ
   ใช้ service หรือเมื่อมีสิ่งใดนอก module ledger เขียนตาราง ledger หรือตารางยอดคงเหลือ

## ผลที่ตามมา

- ระบบยืนยันตัวตน บทบาท audit outbox การออกเลขเอกสาร และโครงหน้าจอ เริ่มจากโค้ดที่พิสูจน์แล้ว ไม่ต้องเขียน
  ใหม่ เวลาราว 1 สัปดาห์จากแผน 6 สัปดาห์จึงไปอยู่กับโดเมนแทน
- ผลิตภัณฑ์สองตัวของผู้ดูแลใช้ stack และข้อตกลงเดียวกัน ดูแลง่ายขึ้น และประเมินคู่กันได้ง่ายขึ้น
- โค้ดที่คัดลอกมาอาจค่อยๆ ต่างจาก Cwork ยอมรับได้สำหรับ v1 การแยกเป็น package ร่วมค่อยพิจารณาเมื่อมี
  โปรเจกต์ที่สามต้องใช้ส่วนเดียวกัน
- `CODING_STANDARDS.md` ของ PaynEat POS (Express และ Flutter) ไม่ใช้กับ repo นี้ ใช้ข้อตกลงเรื่อง module
  และ domain ของ Cwork แทน ซึ่งจะถูกเขียนลง repo นี้ในทิกเก็ตโครงระบบแรก (walking skeleton)
- ความสะดวกของ Prisma ใช้ได้ทุกที่ ยกเว้นจุดเดียวที่มันอาจทำลายกฎของบัญชีเคลื่อนไหวได้โดยไม่มีใครเห็น

## ทางเลือกที่พิจารณาแล้ว

- **Express + Kysely** (ตัวเลือกแรกในช่วงออกแบบ) ถูกแทนที่ก่อนเริ่มเขียนโค้ด เพราะจะต้องสร้างระบบยืนยันตัวตน
  สิทธิ์ audit outbox และโครงหน้าจอใหม่ ทั้งที่ Cwork มีอยู่แล้ว ส่วนข้อดีหลักคือ SQL ที่มองเห็นได้สำหรับ
  บัญชีเคลื่อนไหว ยังคงไว้ได้ด้วยข้อ 4
- **ใช้ Prisma ทุกที่ รวมถึงการ post บัญชีเคลื่อนไหว** ปฏิเสธ: การล็อกแถวและการ post แบบทั้งหมดหรือไม่มีเลย
  ต้องมองเห็นได้ในโค้ดที่ทำงานนั้น
- **แยกโค้ดจาก Cwork เป็น npm package ร่วมตั้งแต่ตอนนี้** ปฏิเสธสำหรับ v1: ค่าใช้จ่ายในการจัดการเวอร์ชัน
  package ข้ามสอง repo มากกว่าเวลาที่ประหยัดได้ภายใน 6 สัปดาห์
