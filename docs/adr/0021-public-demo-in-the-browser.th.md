# ADR-0021: เดโมสาธารณะของ console ที่ทำงานในเบราว์เซอร์ ด้วยกฎชุดเดียวกับ backend

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-26
- **English:** [0021-public-demo-in-the-browser.md](0021-public-demo-in-the-browser.md)

## บริบท

ตอนนี้ไม่มีใครลอง ERP ได้โดยไม่ต้องใช้ Docker PaynEat POS มีเดโมสาธารณะบน GitHub Pages ที่ใครก็เปิดได้ เจ้าของโปรเจกต์ต้องการ
แบบเดียวกันสำหรับ console ของ ERP (#41) และเลือกทางนี้แทนการติดตั้งบนเซิร์ฟเวอร์ (handoff หลัง #34 ทาง A และ B)

GitHub Pages เสิร์ฟได้แค่ไฟล์ static ไม่มี API และไม่มีฐานข้อมูล เดโมบน Pages จึงต้องตอบคำขอของ console จากในเบราว์เซอร์เอง
ความเสี่ยงที่ ADR นี้จัดการอยู่ตรงนี้ ถ้าเขียนโดเมนขึ้นใหม่อีกชุดในเบราว์เซอร์ มันจะค่อยๆ ต่างจากของจริง แล้วผู้เยี่ยมชมจะเห็น
พฤติกรรมที่ ERP จริงไม่มี ซึ่งเท่ากับนำเสนอสิ่งที่ไม่จริงว่าเป็นตัวผลิตภัณฑ์ และ CLAUDE.md ห้ามไว้

[ADR-0020](0020-distribution-and-installation.th.md) ข้อ 2.2 วาง "เดโมออนไลน์สาธารณะ" ไว้หลัง pilot ซึ่งหมายถึงเดโมที่
**โฮสต์จริง** มี API และฐานข้อมูลจริง ADR นี้ไม่เปลี่ยนข้อนั้น แต่เพิ่มเดโมแบบ static ขึ้นมาตอนนี้ ส่วนเดโมที่โฮสต์จริงพร้อมข้อมูลจริง
ยังมาหลัง pilot ตามเดิม

## การตัดสินใจ

1. **มีเดโมสาธารณะของ console บน GitHub Pages** ที่ `https://suruchboss.github.io/PaynEat-ERP/` เป็นโค้ดของ console
   ชุดเดียวกัน build ด้วย `VITE_ERP_DEMO=1` API client ของ console ไม่ได้แก้ มี demo API ในเบราว์เซอร์คั่นอยู่หน้า `fetch`
   ตอบ `/api/v1/*` และ `/health` แทน token, การ refresh, request id และการจัดการ error จึงทำงานเหมือนบนระบบที่ติดตั้งจริง
   และไม่มีคำขอใดออกนอก origin
2. **ข้อมูลคือเชนสมมติของ demo seed เท่านั้น** เดโม import module เดียวกับที่ seed ของ backend ใช้สร้างข้อมูล
   (`backend/prisma/demo-data.ts`) ส่วนเดียวที่ import ไม่ได้คือรายการหน่วยนับ (สร้างใน migration) ซึ่งมีเทสต์เทียบกับ
   migration นั้น ข้อมูลอยู่ในหน่วยความจำตลอดการเข้าชมหนึ่งครั้ง และโหลดหน้าใหม่ก็เริ่มจาก seed อีกครั้ง session ที่เข้าสู่ระบบไว้
   อยู่รอดข้ามการโหลดหน้าใหม่ และมีแต่บัญชีเดโมที่เปิดเผยไว้แล้วเท่านั้น
3. **เดโมไม่ใช่โดเมนชุดที่สอง**
   - **กฎทางธุรกิจทุกข้อที่เป็น pure function ต้อง import มาจาก backend ห้ามเขียนใหม่** ได้แก่ไฟล์ใน `domain/` (ทศนิยม
     แบบแม่นยำและมูลค่าสต๊อก วันที่ทางธุรกิจ รหัสสถานที่และกฎการแทนที่ หน่วยซื้อ เลขประจำตัวผู้เสียภาษี นโยบายรหัสผ่าน
     บรรทัดยอดยกมาและเหตุที่ post ไม่ได้ กฎห้ามสต๊อกติดลบของบัญชีสต๊อก การกลับรายการ เลข lot) และ
     `core/security/permissions.ts` มี lint rule กำหนดว่าเดโม import ไฟล์ไหนของ backend ได้บ้าง และ CI build เดโมทุก
     pull request ถ้ากฎใน backend เปลี่ยนจนเดโม import ไม่ได้ จะพังที่ CI ไม่ใช่บนเว็บจริง
   - **สิ่งที่เดโมเขียนเองมีแค่สิ่งที่ service ของ backend ทำรอบกฎเหล่านั้น** คือลำดับการตรวจ รหัส error และรายละเอียด และ
     รูปแบบของ response รวมถึงการตรวจรูปแบบคำขอตาม DTO มีเทสต์ครอบการเขียนและการปฏิเสธของทุกหน้าจอ
   - **อะไรที่เดโมทำตามกฎได้ไม่ตรง จะบอกตรงๆ ด้วย `NOT_IN_DEMO` และไม่ประมาณเอา** console จะแสดงว่า "ยังไม่มีในเดโม"
     กฎข้อเดียวที่ import ไม่ได้คือรหัสยืนยันตัวตนขั้นที่สอง เพราะ backend ใช้ crypto ของ Node ซึ่งเบราว์เซอร์ไม่มี เดโมจึง
     คำนวณรหัส RFC 6238 แบบเดียวกันด้วย Web Crypto และมีเทสต์เทียบกับฟังก์ชันของ backend เองและชุดทดสอบของ RFC
   - บางอย่างเดโมไม่มี เพราะไม่มีหน้าจอไหนแสดง ได้แก่บันทึกการตรวจสอบ บันทึกการเปลี่ยน master data การจำกัดอัตราคำขอ
     และการ hash รหัสผ่าน ซึ่งรหัสผ่านเปิดเผยอยู่แล้ว
4. **ขอบเขตในอนาคต: เดโมครอบคลุมหน้าจอที่มีอยู่ตอนเผยแพร่ ทิกเก็ตถัดไปจะขยายเดโมก็ได้ แต่ไม่บังคับ** ณ #41 ได้แก่ สถานะระบบ
   ผู้ใช้และบทบาท สินค้า สถานที่ ซัพพลายเออร์ สต๊อกคงเหลือ และยอดยกมา path ไหนที่ demo API ไม่ได้ให้บริการ จะตอบ
   `NOT_IN_DEMO` หน้าจอที่เพิ่มทีหลังจึงบอกว่า "ยังไม่มีในเดโม" แทนที่จะพังแบบอื่น ไม่มีทิกเก็ตไหนรับภาระที่ไม่ได้เขียนไว้
   และทิกเก็ตที่ขยายเดโมต้องระบุไว้เอง
5. **ดูออกเสมอว่าเป็นเดโม** แถบ "ระบบเดโม" (#5) อยู่ทุกหน้าจอ และบอกเพิ่มว่าไม่มีเซิร์ฟเวอร์และสิ่งที่แก้ไม่ถูกเก็บไว้
   หน้าเข้าสู่ระบบแสดงบัญชีเดโมที่เปิดเผยไว้และรหัสกู้คืนของผู้ดูแลระบบ
6. **build ปกติไม่มีเดโมติดไปเลย** เดโมโหลดเฉพาะหลังค่าคงที่ตอน build ผ่าน dynamic import ที่ build ปกติตัดทิ้ง และ CI ตรวจ
   ทั้งสอง build ด้วย `web/scripts/check-demo-build.mjs`
   - เครื่องหมายของ demo API และรหัสผ่านที่เปิดเผยต้องอยู่ใน build เดโมเท่านั้น
   - build เดโมต้องมี `<meta>` ของ policy และ `404.html`
7. **เรื่องเฉพาะของ GitHub Pages**
   - base path คือ `/PaynEat-ERP/` (Vite `base` และ `basename` ของ router)
   - `404.html` เป็นสำเนาของ `index.html` ลิงก์ตรงอย่าง `/PaynEat-ERP/items` จึงเปิด console ได้ แต่ Pages ยังตอบลิงก์
     นั้นด้วยสถานะ 404 ซึ่งเห็นได้แค่ใน developer tools ของเบราว์เซอร์
   - Pages ไม่ส่ง response header ของเรา `web/security-headers.conf` จึงใช้ไม่ได้ เดโมใส่ Content-Security-Policy ของไฟล์นั้น
     เป็น `<meta>` แทน **โดยไม่มี `frame-ancestors`** ซึ่ง `<meta>` ใส่ไม่ได้ ผลคือเว็บอื่นฝังเดโมใน frame ได้ และไม่มี
     `X-Frame-Options`, `nosniff`, `Referrer-Policy` และ `Permissions-Policy` ยอมรับได้เพราะเดโมไม่มีข้อมูลจริง และไม่มี
     รหัสผ่านใดนอกจากที่เปิดเผยไว้แล้ว
8. **deploy ด้วย `.github/workflows/deploy-pages.yml`** ทุกครั้งที่ push เข้า `main` แล้วแก้ console หรือไฟล์ของ backend
   ที่เดโม import และเมื่อกดรันเอง จะเผยแพร่เฉพาะ build ที่เทสต์ผ่าน เจ้าของโปรเจกต์ต้องเปิด Pages ครั้งเดียว
   (Settings → Pages → Source: GitHub Actions)

## ผลที่ตามมา

- ไฟล์กฎแบบ pure ของ backend ใช้ร่วมกับ console แล้ว จึง**ต้อง pure ต่อไป และใช้เฉพาะ TypeScript ที่ลบ type ออกแล้วเป็น
  JavaScript ได้เลย** (ห้าม parameter property และ enum) #41 ย้ายข้อมูลเดโมจาก `prisma/seed.ts` ไปไว้ที่
  `prisma/demo-data.ts` และเปลี่ยน `ConversionError` จาก parameter property เป็น field ธรรมดา โดยพฤติกรรมไม่เปลี่ยน
- Docker image ของ console build จาก root ของ repository เพราะการตรวจ type ต้องเห็นไฟล์ของ backend ที่เดโม import
  `web/Dockerfile.dockerignore` จำกัด build context ไว้ที่ `web/` กับไฟล์เหล่านั้น และตัว image ไม่มีโค้ดเดโมเลย
- เมื่อพฤติกรรมของ API หลังหน้าจอที่มีอยู่แล้วเปลี่ยน ให้แก้ `web/src/demo` ใน pull request เดียวกัน กฎตามมาเองได้ แต่ลำดับ
  การทำงานไม่ตามมาเอง CLAUDE.md เขียนไว้แล้ว
- สถานที่ระหว่างขนส่งปรากฏในเดโมตรงกับที่ console จริงแสดง คือรายการสถานที่และสต๊อกคงเหลือ ไม่ถูกเสนอในที่ที่ต้องการสถานที่
  เก็บสต๊อก และไม่เข้าบันทึกการเปลี่ยน master data เพราะมีแค่สาขาที่ได้เวอร์ชัน master data (#6) เดโมใช้โค้ดชุดเดียวกัน
  ทั้งสองเรื่อง
- โค้ดเดโมประมาณ 2,700 บรรทัด ส่วนใหญ่เป็นลำดับการทำงานของ service และรูปแบบ response

## ทางเลือกที่พิจารณา

- **เดโมที่โฮสต์จริงพร้อม API และฐานข้อมูลตอนนี้เลย** ยังไม่เลือกตอนนี้ เพราะเป็นเดโมหลัง pilot ตาม ADR-0020 ต้องมีเซิร์ฟเวอร์
  โดเมน TLS secrets ค่าใช้จ่ายรายเดือน รอบการรีเซ็ตข้อมูล และการรับมือการใช้งานในทางที่ผิด ก่อนที่จะมีเชนใดใช้ ERP
- **คัดลอกกฎมาไว้ใน console** ไม่เลือก เพราะทุกสำเนาต่างจาก backend ได้ และความต่างนั้นจะไปแสดงต่อผู้เยี่ยมชมว่าเป็นตัวผลิตภัณฑ์
- **ใช้ไลบรารีจำลอง (Mock Service Worker) หรือคำตอบที่บันทึกไว้** ไม่เลือก เพราะเพิ่ม dependency และเพิ่ม service worker
  ที่ console แบบติดตั้งได้ในอนาคต (ADR-0020) ต้องอยู่ร่วมด้วย และคำตอบที่บันทึกไว้ปฏิเสธข้อมูลใหม่แบบที่กฎทำไม่ได้
- **รัน backend NestJS ทั้งตัวในเบราว์เซอร์** พร้อมฐานข้อมูลในเบราว์เซอร์ ไม่เลือก เพราะ NestJS, Prisma และ argon2 ไม่ทำงานใน
  เบราว์เซอร์ และการทำให้ทำงานได้มีต้นทุนสูงเกินคุณค่าของเดโม
- **มีแค่ภาพหน้าจอและวิดีโอ** ไม่เลือก เพราะไม่มีอะไรให้ลองจริง
