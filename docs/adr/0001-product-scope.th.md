# ADR-0001: ขอบเขตผลิตภัณฑ์ — ERP สำหรับเครือร้านอาหารที่ควบคุมห่วงโซ่อุปทานของตัวเองครบวงจร (vertically integrated)

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-25
- **English:** [0001-product-scope.md](0001-product-scope.md)

## บริบท

PaynEat เริ่มต้นจากการเป็นระบบขายหน้าร้าน (point-of-sale) สำหรับร้านอาหารร้านเดียว แต่เครือร้านอาหารสำหรับตลาดแมส
มีกลไกที่ใหญ่กว่ามากทำงานอยู่เบื้องหลังเครื่องคิดเงิน: ต้องซื้อวัตถุดิบจากซัพพลายเออร์จำนวนมากในจังหวะที่เหมาะสม
แปรรูปในโรงงานของตัวเอง (เช่น แยกชิ้นไก่ทั้งตัวเป็นชิ้นส่วนตามสัดส่วนที่กำหนด) ส่งผลผลิตไปยังสาขา แล้วจึงขายให้ลูกค้า
ERP แบบโอเพนซอร์สส่วนใหญ่เป็นระบบทั่วไป และปล่อยให้ส่วนกลางที่เฉพาะของธุรกิจอาหาร — lot วันหมดอายุ อัตราผลได้
ห่วงโซ่ความเย็น (cold chain) การย้อนรอย — เป็นเรื่องที่ผู้นำระบบไปติดตั้งต้องไปทำเอง

ตัววัดความสำเร็จของโปรเจกต์นี้คือ **คนที่เคยดูแลระบบ ERP ในธุรกิจบริการอาหารหรือธุรกิจแปรรูปอาหาร อ่าน repository
นี้แล้วเห็นได้ว่าโดเมนถูกจำลองไว้อย่างถูกต้อง** การใช้เป็นผลงานในพอร์ตโฟลิโอได้เป็นผลที่ตามมาจากข้อนั้นเอง ส่วนยอด
ดาวน์โหลดและจำนวนดาว (stars) ไม่ใช่เป้าหมาย

## การตัดสินใจ

PaynEat ERP ครอบคลุมฝั่งอุปทาน (supply side) ของเครือร้านอาหารหนึ่งเครือที่ควบคุมห่วงโซ่ของตัวเองตั้งแต่ต้นจนจบ:

1. **การจัดซื้อ** — ซัพพลายเออร์ ใบสั่งซื้อ ใบรับสินค้าพร้อมการตรวจรับ ใบส่งคืนสินค้า
2. **การผลิต** — โรงงาน**ของบริษัทเอง**แปรรูป lot วัตถุดิบนำเข้า (input lot) เป็น lot ผลผลิต (output lot) โดยวัด
   อัตราผลได้จริงและปันต้นทุน งานแปรรูปโดยโรงงานรับจ้างได้ออกแบบรองรับไว้แล้ว (สงวนประเภทสถานที่เก็บสต๊อกไว้
   หนึ่งประเภท) แต่ยังไม่ได้สร้าง
3. **การกระจายสินค้า** — ใบขอเบิกของสาขา การโอนผ่านสถานที่เก็บสต๊อกระหว่างขนส่ง และการรับที่ผ่านการตรวจรับ
   ทั้งสองฝั่ง
4. **การใช้วัตถุดิบที่สาขา** — ยอดขายจาก PaynEat POS ถูกแปลงเป็นการใช้ตามทฤษฎีผ่านสูตรที่มีการกำหนดเวอร์ชัน
5. **การควบคุม** — บัญชีเคลื่อนไหวสต๊อกแบบเพิ่มได้อย่างเดียว (append-only) การตรวจนับสต๊อก การปิดงวด การย้อนรอย
   lot และการ recall การแยกหน้าที่
6. **การวางแผน** — จุดสั่งซื้อ คำแนะนำใบขอเบิกตามระดับสต๊อกมาตรฐาน และคำแนะนำจาก MRP-lite

สถานการณ์อ้างอิงที่ใช้ในทุกที่ (ข้อมูลตัวอย่าง เทสต์ เอกสาร) คือเครือร้านไก่ทอดสมมติ: โรงงาน 1 แห่ง สาขา 3 แห่ง
ซัพพลายเออร์ 2 ราย

### สิ่งที่อยู่นอกขอบเขตอย่างชัดแจ้ง

| ด้าน | อยู่ที่ใดแทน |
|---|---|
| บัญชีแยกประเภททั่วไป (GL) การจ่ายชำระเจ้าหนี้ งบการเงิน | export ไปยังซอฟต์แวร์บัญชีของบริษัท |
| บุคลากร การลงเวลา การลา เงินเดือน | [Cwork](https://github.com/SuruchBoss/Cwork) ระบบ HRIS โอเพนซอร์สที่เป็นโปรเจกต์คู่กัน การเชื่อมระบบเป็นงานในอนาคต (ดูหัวข้อผลที่ตามมา) |
| การสั่งอาหาร การชำระเงิน และใบกำกับภาษีฝั่งลูกค้า | [PaynEat POS](https://github.com/SuruchBoss/PaynEat) |
| หลายบริษัทในการติดตั้งชุดเดียว | ไม่รองรับ การติดตั้งหนึ่งชุดให้บริการบริษัทเดียว |
| ERP ของซัพพลายเออร์เอง | ไม่ใช่สิ่งที่เราต้องสร้าง |

## ผลที่ตามมา

- รุ่นแรก (first release) จะถูกตัดสินจากเส้นทางต้นจนจบเพียงเส้นทางเดียวที่ต้องทำงานได้ถูกต้องแม่นยำ: ซื้อไก่ → รับเข้า
  พร้อม lot → แยกชิ้นพร้อมวัดอัตราผลได้ → โอนไปสาขา → ขายบน POS → ย้อนรอยจานที่ขายไปกลับไปหา lot ที่เป็นไปได้
  ของซัพพลายเออร์ ความกว้างของฟีเจอร์ถูกแลกกับความลึกนี้อย่างจงใจ
- สิ่งที่เลื่อนออกไป ซึ่งบันทึกไว้ที่นี่เพื่อให้เป็นการตัดสินใจ ไม่ใช่การตกหล่น: การจับคู่ใบแจ้งหนี้สามทาง (three-way
  invoice matching; เป็นเป้าหมายเสริม (stretch goal) ของ v1) ต้นทุนมาตรฐาน (standard costing) catch-weight
  เต็มรูปแบบ งานแปรรูปโดยโรงงานรับจ้าง การสแกน lot รายแพ็กที่สาขา การพยากรณ์ความต้องการและการกำหนดจังหวะการซื้อ
  (AI agent ในอนาคต) แอปแท็บเล็ตสำหรับการรับสินค้าและการตรวจนับ และการย้าย PaynEat POS เองไปใช้ PostgreSQL
- **การเชื่อมกับ Cwork (อนาคต)** Cwork มีโมเดล `WorkLocation` แผนกที่มี `costCenter` การลงเวลาแยกตามสถานที่
  ทำงาน รอบการจ่ายเงินเดือน และ transactional outbox อยู่แล้ว รูปแบบที่คาดไว้คือ: สถานที่เก็บสต๊อกใน ERP จับคู่แบบ
  หนึ่งต่อหนึ่งกับสถานที่ทำงานใน Cwork ด้วยรหัสที่คงที่ ต้นทุนเงินเดือนต่อศูนย์ต้นทุนต่องวดไหลเข้า ERP เป็นต้นทุน
  แรงงานสำหรับรายงานต้นทุนของสาขาและโรงงาน ส่วนชั่วโมงการลงเวลาต่อสถานที่ทำงานช่วยให้วัดผลิตภาพแรงงานได้ (เช่น
  ยอดขายต่อชั่วโมงแรงงาน) เพื่อให้การเชื่อมนี้ทำได้ด้วยต้นทุนต่ำ **สถานที่เก็บสต๊อกทุกแห่งใน ERP ต้องมีรหัสที่คงที่และ
  คนอ่านเข้าใจได้ตั้งแต่วันแรก**
- เนื่องจาก GL อยู่นอกขอบเขต ตัวเลขทางการเงินทุกตัวที่ ERP คำนวณ (มูลค่าสต๊อก ต้นทุนสินค้าที่ใช้ไป ส่วนต่าง)
  ต้อง export แยกตามงวดได้

## ทางเลือกที่พิจารณา

- **ERP ทั่วไปที่มีโมดูลสำหรับทุกแผนก** ปฏิเสธ: โมดูลที่ทำได้ครึ่งๆ กลางๆ จำนวนมากพิสูจน์อะไรได้น้อยกว่าเส้นทางเดียว
  ที่ทำงานได้ถูกต้องแม่นยำ และปัญหาเฉพาะของธุรกิจอาหารคือจุดที่จะสร้างความน่าเชื่อถือได้
- **ERP สำหรับโรงงานแปรรูปที่เป็นธุรกิจของตัวเอง (ขายให้ลูกค้าจำนวนมาก)** ปฏิเสธ: เป็นผลิตภัณฑ์คนละตัว มีลูกค้า
  คนละกลุ่ม
- **สร้างระบบ HR และเงินเดือนไว้ใน ERP** ปฏิเสธ: Cwork ทำส่วนนี้ได้อย่างถูกต้องตามแนวปฏิบัติด้านแรงงานของไทยอยู่แล้ว
  การทำซ้ำจะได้ผลด้อยกว่าการเชื่อมต่อกับ Cwork
