# ADR-0019: ปริมาณเป็นทศนิยมแบบแม่นยำ และกฎการปัดเศษเดียวสำหรับการแปลงหน่วย

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-26
- **English:** [0019-exact-quantities-and-conversion-rounding.md](0019-exact-quantities-and-conversion-rounding.md)

## บริบท

ADR-0005 กำหนดให้ทุกรายการสินค้ามีหน่วยหลักหน่วยเดียว และแปลงหน่วยซื้อเป็นหน่วยหลักด้วยตัวคูณคงที่ (ลัง → กิโลกรัม)
#5 สร้างการแปลงหน่วยนี้ และทุกการรับสินค้า การโอน และการตรวจนับหลังจากนี้จะใช้มัน มีสองเรื่องที่ทำให้บัญชีสต๊อก
ซึ่งต้องลงตัวถึงระดับกรัมผิดเพี้ยนได้โดยไม่มีใครสังเกต:

- **เลขทศนิยมฐานสอง (floating point)** ตัวเลขของ JavaScript เก็บ 0.1 ได้ไม่ตรง: `0.1 * 3` ได้
  `0.30000000000000004` ปริมาณที่ผ่านตัวเลขแบบนี้ก่อนถึงฐานข้อมูลจะคลาดไปเล็กน้อย และผลรวมของค่าเหล่านี้จะเพี้ยนสะสม
- **การปัดเศษที่แต่ละที่ตัดสินใจเอง** 1 แพ็กขนาด 12.5 กรัมคิดเป็น 0.0125 กิโลกรัม ถ้าเก็บถึงระดับกรัมจะกลายเป็น
  0.012 หรือ 0.013 แล้วแต่ว่าใครเขียนหน้าจอนั้น ถ้า API รายงาน และฐานข้อมูลปัดต่างกัน รายการเคลื่อนไหวเดียวกันจะมีสามค่า

ตัวคูณที่เป็นศูนย์หรือติดลบคือความเสี่ยงที่สาม: ลังที่ "บรรจุ" 0 กิโลกรัมทำให้ของที่ส่งมาหายไปเฉยๆ และตัวคูณติดลบ
ทำให้การรับของกลายเป็นการเบิกออก

## การตัดสินใจ

1. **ปริมาณและตัวคูณเป็นทศนิยมแบบแม่นยำทุกที่** ผ่าน API เป็นสตริงทศนิยม (`"22.5"` ไม่ใช่ตัวเลข JSON)
   ใน PostgreSQL เป็น `NUMERIC` และใน domain เป็นจำนวนเต็มของหน่วยย่อยที่สุดเก็บใน `bigint`
   (`backend/src/core/quantity/domain/exact-decimal.ts`) ไม่มีปริมาณหรือตัวคูณใดผ่านเลขทศนิยมฐานสอง
2. **ทุกหน่วยนับเก็บปริมาณด้วยจำนวนทศนิยมที่กำหนดไว้กับหน่วยนั้นเอง**: 3 ตำแหน่งสำหรับกิโลกรัมและลิตร
   (ระดับกรัม มิลลิลิตร) และ 0 สำหรับชิ้น ลัง ถุง และหน่วยนับอื่นๆ รายการหน่วยนับมาพร้อมกับแต่ละรุ่นที่ออก
   (migration) และเหมือนกันทุกการติดตั้ง
3. **ตัวคูณแปลงหน่วยต้องมากกว่าศูนย์** มีทศนิยมไม่เกิน 6 ตำแหน่ง และมีหลักหน้าจุดไม่เกิน 12 หลัก
   (เก็บเป็น `NUMERIC(18,6)`) API ปฏิเสธค่าอื่นทั้งหมดโดยระบุแถวและเหตุผล และฐานข้อมูลปฏิเสธตัวคูณที่ไม่เป็นบวก
   ซ้ำอีกชั้น
4. **การแปลงปริมาณหน่วยซื้อเป็นหน่วยหลัก** คูณแบบแม่นยำแล้ว **ปัดเศษครั้งเดียว แบบครึ่งหนึ่งปัดออกจากศูนย์
   (half away from zero) ตามจำนวนทศนิยมของหน่วยหลัก** ซึ่งเป็นกฎเดียวกับ `round(numeric, n)` ของ PostgreSQL
   API กับรายงานที่เขียนด้วย SQL จึงไม่มีวันได้ค่าต่างกัน: 3 ลัง × 20 กิโลกรัม = `30.000` กิโลกรัม,
   1 แพ็ก × 0.0125 กิโลกรัม = `0.013` กิโลกรัม และการคืนแพ็กเดียวกันเป็น `-0.013` กิโลกรัม ปัดผลคูณที่แม่นยำ
   ไม่ใช่ปัดตัวคูณก่อน
5. **ปริมาณที่ใส่ในหน่วยใดต้องไม่ละเอียดเกินกว่าที่หน่วยนั้นยอมรับ**: 2.5 ลังถูกปฏิเสธ ไม่ถูกปัดเป็น 2 หรือ 3
6. **หน่วยหลักของรายการสินค้าเปลี่ยนไม่ได้หลังสร้าง** และรหัสสินค้าก็เช่นกัน ทุกปริมาณที่บันทึกไว้ของรายการนั้นอยู่ใน
   หน่วยนั้น การเปลี่ยนหน่วยจะเปลี่ยนสเกลของทุกค่าโดยไม่มีใครรู้ ถ้าหน่วยหลักผิด ให้สร้างรายการใหม่แล้วปิดใช้งาน
   รายการเดิม

## ผลที่ตามมา

- การแปลงหน่วยเป็นฟังก์ชันบริสุทธิ์ (pure function) ตัวเดียวที่มี unit test
  (`backend/src/modules/items/domain/unit-conversion.ts`) การรับสินค้า การโอน และการตรวจนับใช้ตัวเดียวกันนี้
- ฝั่งที่เรียก API (console, POS, ExcelToGo) ส่งและรับปริมาณเป็นสตริง และไม่คำนวณด้วยเลขทศนิยมฐานสอง console
  แสดงสตริงที่ API ส่งมาตามนั้น
- การปัดเศษเกิดครั้งเดียวตอนแปลงหน่วย เอกสารเก็บปริมาณตามที่ใส่ในหน่วยที่ใส่ ไว้คู่กับปริมาณหน่วยหลักที่แปลงแล้ว
  การปัดเศษจึงมองเห็นและอธิบายได้เสมอ
- หน่วยที่ไม่มีในรายการต้องรอรุ่นถัดไป ยอมรับสำหรับ v1: รายการหน่วยครอบคลุมเส้นทางของเชน และหน่วยนับเปลี่ยนไม่บ่อย

## ทางเลือกที่พิจารณาแล้ว

- **ใช้ตัวเลขของ JavaScript แล้วปัดเศษที่ขอบระบบ** ไม่เลือก: ค่าผิดไปแล้วก่อนถึงขอบใดๆ และทุกหน้าจอใหม่คือโอกาสใหม่
  ที่จะลืมปัด
- **ปัดแบบธนาคาร (half to even)** ไม่เลือก: มันลดความเอนเอียงทางสถิติที่ไม่มีผลในระดับการส่งของหนึ่งครั้ง และไม่ตรงกับ
  `round()` ของ PostgreSQL และกับที่คนตรวจด้วยมือหรือในสเปรดชีตคาดหวัง
- **ให้แต่ละรายการสินค้ากำหนดความละเอียดเอง** ไม่เลือกสำหรับ v1: หน่วยนับบอกอยู่แล้วว่านับละเอียดแค่ไหน การให้
  รายการสินค้ากำหนดทับเพิ่มได้ภายหลังโดยไม่ต้อง migrate ประวัติ
- **เก็บแค่ปริมาณหน่วยหลัก** ไม่เลือก: ปริมาณหน่วยซื้อคือสิ่งที่ซัพพลายเออร์ออกใบแจ้งหนี้ การทิ้งมันซ่อนการปัดเศษ และทำให้
  การจับคู่เอกสารสามทางยากขึ้นในภายหลัง
