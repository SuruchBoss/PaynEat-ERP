# ADR-0013: ต่อยอดผ่านการเชื่อมต่อ ไม่ใช่ plugin ที่รันภายใน ERP

- **สถานะ:** ยอมรับแล้ว; ใช้กับโค้ดของคนนอก — โค้ด Enterprise ของเราเองใน `ee/` อยู่ภายใต้ [ADR-0015](0015-editions-community-and-enterprise.th.md)
- **วันที่:** 2026-09-25
- **English:** [0013-extension-by-integration.md](0013-extension-by-integration.md)

## บริบท

ทุกเชนมีความต้องการที่โปรเจกต์นี้จะไม่สร้างให้ เช่น โปรแกรมบัญชีเฉพาะยี่ห้อ แพลตฟอร์ม delivery พอร์ทัลของ
ซัพพลายเออร์ หรือรายงานที่ฝ่ายการเงินเจ้าเดียวต้องการ ERP แบบ open source ที่ต่อยอดไม่ได้จะบังคับให้เชนเหล่านั้น fork
ออกไป และ fork จะไม่ได้รับการอัปเกรดอีก

คำตอบที่คุ้นเคยคือระบบ module หรือ plugin แบบ Odoo: โหลดโค้ดของคนอื่นเข้ามารันใน process เดียวกับ ERP เพิ่มตาราง
หน้าจอ และพฤติกรรมได้ แต่โมเดลนี้มีต้นทุนที่กระทบกฎหลักของโปรเจกต์นี้โดยตรง:

- **บัญชีเคลื่อนไหวสต๊อก** ยอดสต๊อกคือบัญชีแบบ append-only ที่ post โดย module บัญชีสต๊อกเท่านั้น ด้วย SQL ตรง
  และล็อกแถวตามลำดับเดียวกันเสมอ (ADR-0003, ADR-0010) โค้ดที่รันใน process เดียวกันและใช้ connection ฐานข้อมูล
  เดียวกันเขียนตารางเหล่านั้นตรงๆ ได้ plugin ตัวเดียวแบบนั้นก็ทำให้ยอดทุกยอดในระบบเชื่อไม่ได้แล้ว
- **การอัปเกรด** ระดับ 2 ใน ADR-0012 หมายถึงการอัปเกรดที่ไม่ทำให้ข้อมูลเสียหาย plugin ที่พึ่ง class ภายในหรือ
  โครงสร้างตารางจะพังเมื่อ refactor ครั้งถัดไป ผู้ดูแลต้องเลือกระหว่างเลิก refactor หรือทำให้ระบบของคนอื่นพัง
- **จังหวะเวลา** API สำหรับ plugin ทำให้ interface ภายในถูกแช่แข็ง การแช่แข็งก่อน release แรกจะมีผู้ใช้จริง
  คือการล็อกสิ่งที่เดาไว้ในสัปดาห์แรก
- **ขอบเขต** ADR-0012 จัดระบบ module ไว้ที่ระดับ 3 ซึ่งยังไม่ใช่เป้าจนกว่าจะมีชุมชนผู้ร่วมพัฒนา

ระบบนิเวศเชื่อมกันแบบนี้อยู่แล้ว: POS, Cwork และ SherWhyve เป็นระบบแยกกันที่เชื่อมด้วยสัญญาที่มีเวอร์ชัน
(ADR-0002, ADR-0011) ส่วนเสริมจากคนนอกก็เป็นผู้ร่วมวงอีกรายภายใต้เงื่อนไขเดียวกันได้

## การตัดสินใจ

1. **ต่อยอด ERP จากภายนอก ผ่านสัญญาสามอย่าง:**

   | สัญญา | ส่วนเสริมได้อะไร |
   |---|---|
   | **Public API ที่มีเวอร์ชัน** | อ่าน master data ยอดคงเหลือ lot และเอกสารที่ post แล้ว; สร้างเอกสารฉบับร่างที่ยังต้องผ่านกฎการอนุมัติและการ post ของ ERP เอง มีเวอร์ชันใน path (`/api/v1/...`) และประกาศระยะเวลายกเลิกล่วงหน้าก่อนถอดเวอร์ชันใดออก |
   | **API token แบบจำกัดสิทธิ์** | token เป็นของการเชื่อมต่อ ไม่ใช่ของคน และระบุ scope ชัดเจน (เช่น `items:read`, `documents:draft`) ไม่มี scope ใดให้ post อนุมัติ หรือทำสิ่งที่บทบาทใน ADR-0008 สงวนไว้ให้คน token เพิกถอนได้ และทุกการเรียกถูกบันทึกใน audit trail ว่ามาจากการเชื่อมต่อไหน |
   | **Webhook ขาออก** | event ของเอกสารที่ post แล้วและ master data ส่งออกจาก transactional outbox ตัวเดียวกับที่สัญญา POS ใช้: มีลายเซ็น, ส่งซ้ำแบบเว้นระยะเมื่อล้มเหลว, มี idempotency key และเวอร์ชันสัญญา ผู้รับจึงประมวลผลแต่ละ event ได้ครั้งเดียวพอดี |

2. **ไม่มี plugin ที่รันภายใน** ERP ไม่โหลดโค้ดของคนอื่น และส่วนเสริมเข้าถึงฐานข้อมูลไม่ได้ บัญชีเคลื่อนไหวสต๊อก
   ต้นทุน และกฎการ post อยู่ในการควบคุมของ ERP แต่ผู้เดียว
3. **ส่วนเสริมเป็นบริการแยก** เขียนด้วยภาษาอะไรก็ได้ deploy และอัปเกรดตามรอบของตัวเอง ถ้าต้องการให้สืบสวนได้ใน
   ระบบนิเวศ ต้องทำตามสัญญา telemetry (`docs/TELEMETRY.md`) และถูกระบุตัวด้วย token ไม่ใช่การ login ของคน
4. **จังหวะเวลา** สร้างสัญญาเหล่านี้หลัง release แรก เมื่อโมเดลภายในผ่านการใช้งานจริงบนเส้นทาง end-to-end แล้ว
   สัญญา POS (ADR-0002) คือตัวอย่างแรกของแนวทางนี้และจะเป็นแม่แบบให้ส่วนที่เหลือ
5. **พิจารณาใหม่** เรื่องการต่อยอดแบบรันภายในก็ต่อเมื่อเกิดชุมชนผู้ร่วมพัฒนาขึ้นจริง (ADR-0012 ระดับ 3) และต้อง
   ออกเป็น ADR ใหม่ที่อธิบายว่ากฎของบัญชีเคลื่อนไหวสต๊อกยังรักษาไว้ได้อย่างไร

## ผลที่ตามมา

- โค้ดของคนอื่นทำให้การอัปเกรดพังไม่ได้ เพราะไม่มีโค้ดของคนอื่นรันใน ERP สิ่งเดียวที่ต้องคงที่คือสัญญา public API
  ซึ่งมีเวอร์ชันชัดเจน
- ทุกการเปลี่ยนแปลงจากส่วนเสริมผ่านเส้นทาง ร่าง → อนุมัติ → post เหมือนของคน การแยกหน้าที่ (ADR-0008) และกฎของ
  บัญชีเคลื่อนไหวสต๊อก (ADR-0003) จึงไม่มีข้อยกเว้น
- ส่วนเสริมทำได้น้อยกว่า module ของ Odoo: เพิ่มหน้าจอใน web console ไม่ได้ เพิ่มฟิลด์ในเอกสารหลักไม่ได้ และ
  เปลี่ยนวิธี post ไม่ได้ ความต้องการที่จำเป็นต้องทำแบบนั้นจริงๆ ถือเป็นคำขอฟีเจอร์ของ ERP เอง และตัดสินด้วย
  คำถามเรื่องขอบเขตใน ADR-0012
- outbox ที่มีอยู่จะมีผู้รับประเภทที่สอง การออกแบบ (idempotency key, payload ที่มีเวอร์ชัน, การส่งซ้ำ) ต้องทั่วไป
  พอสำหรับ webhook ไม่ใช่เฉพาะ POS
- public API ต้องมีเอกสารของตัวเอง (OpenAPI ที่สร้างจากโค้ด) และเทสต์ความเข้ากันได้ย้อนหลังระหว่างเวอร์ชัน ซึ่งกลาย
  เป็นส่วนหนึ่งของวินัยการ release ระดับ 2

## ทางเลือกที่พิจารณาแล้ว

- **ระบบ module ที่รันภายใน (แบบ Odoo)** ปฏิเสธในตอนนี้: เปิดให้โค้ดภายนอกข้ามกฎของบัญชีเคลื่อนไหวสต๊อกและต้นทุน
  ทำให้ทุกการ refactor ภายในกลายเป็นการเปลี่ยนที่ทำให้ของคนอื่นพัง และเป็นขอบเขตระดับ 3 ที่ต้องมีชุมชนซึ่งยังไม่มี
- **script hook ภายใน ERP (รัน script ของผู้ใช้เมื่อเกิด event)** ปฏิเสธ: ปัญหาเรื่องความไว้ใจเดียวกับ plugin
  ในขนาดเล็กลง บวกกับ sandbox ที่ต้องดูแลความปลอดภัย
- **ให้ผู้เชื่อมต่ออ่านฐานข้อมูลตรงแบบอ่านอย่างเดียว** ปฏิเสธ: โครงสร้างตารางจะกลายเป็นสัญญาสาธารณะ ทำให้แก้
  schema ไม่ได้ และข้าม audit trail ความต้องการด้านรายงานใช้ API และ export ในภายหลังแทน
- **ไม่มีทางต่อยอดเลย** ปฏิเสธ: เหลือแค่การ fork ซึ่งไม่ได้รับการแก้ไขหรืออัปเกรด ขัดกับเป้าระดับ 2
