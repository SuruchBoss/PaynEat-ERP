# ADR-0023: ราคาและสูตรของเมนูเริ่มมีผลตามวันที่ทางธุรกิจ และไม่เปลี่ยนอีกเมื่อมีผลแล้ว

- **สถานะ:** Proposed
- **วันที่:** 2026-10-02
- **English:** [0023-menu-prices-and-versioned-recipes.md](0023-menu-prices-and-versioned-recipes.md)

## บริบท

ADR-0002 ให้ ERP เป็นแหล่งความจริงของสิ่งที่สาขาขาย ได้แก่ รายการเมนู ราคา สูตรเมนู และสูตรของตัวเลือกเสริม POS ที่เชื่อมต่อ
เก็บไว้อ่านอย่างเดียว การใช้ตามทฤษฎีแปลงยอดขายแต่ละรายการด้วยสูตร**ที่มีผล ณ เวลาที่ขาย** ADR-0005 เพิ่มว่ายอดขายแบบชั่งน้ำหนัก
มาพร้อมน้ำหนัก และสูตรเมนูกำหนดเป็นต่อกิโลกรัมที่ขายได้ ADR-0018 นับทุกอย่างตามวันที่ทางธุรกิจในเขตเวลาของบริษัท

Issue #16 สร้างส่วนนี้พร้อมสัญญา 1.1 โดยขอสูตรที่มีเวอร์ชัน ไม่ซ้อนกัน และไม่แก้หลังมีผล ขอราคาที่มีวันที่เริ่มมีผลและราคาเฉพาะสาขา
และขอตัวแก้สูตรที่แสดงต้นทุนตามทฤษฎีต่อที่จากต้นทุน lot ปัจจุบัน แต่กติกาเบื้องหลังข้อกำหนดเหล่านี้ยังไม่เคยเขียนไว้หลายข้อ

- "มีผล" แปลว่าอะไร
- เวอร์ชันใหม่เริ่มได้เร็วแค่ไหน
- ถ้าเวอร์ชันหรือราคาผิด แก้ได้หรือไม่
- ราคาสาขากับราคากลางใช้ร่วมกันอย่างไร
- สูตรคิดต้นทุนจาก lot ไหน

แต่ละข้อเปลี่ยนตัวเลขที่รายงานสต๊อกหรือ POS แสดง

## การตัดสินใจ

1. **ราคาและเวอร์ชันสูตรเริ่มมีผลตามวันที่ทางธุรกิจ** (`YYYY-MM-DD` ตามเขตเวลาของบริษัท ADR-0018) เวอร์ชันหนึ่งมีผลตั้งแต่วันที่เริ่ม
   จนกว่าเวอร์ชันถัดไปของสูตรเดียวกันจะเริ่ม ไม่มีวันสิ้นสุดให้ต้องคอยปรับตาม สองเวอร์ชันของสูตรเดียวกันเริ่มวันเดียวกันไม่ได้ ซึ่งเป็นทางเดียว
   ที่จะซ้อนกัน และระบบปฏิเสธ (`RECIPE_VERSION_OVERLAP`) "สูตรที่มีผลในวันที่ D" เป็นฟังก์ชัน domain ล้วน (`recipeInEffect`)
   และ #17 ใช้กับวันที่ทางธุรกิจของการขาย
2. **สูตรไม่เปลี่ยนสำหรับวันที่เริ่มไปแล้ว**
   - เวอร์ชันแรกเริ่มได้ตั้งแต่วันนี้
   - เมื่อมีเวอร์ชันที่มีผลอยู่แล้ว เวอร์ชันใหม่เริ่มได้เร็วสุดพรุ่งนี้ (`RECIPE_TOO_EARLY`) เพราะวันนี้อาจมีการขายด้วยเวอร์ชันที่มีผลอยู่แล้ว
   - เวอร์ชันใหม่แทรกระหว่างสองเวอร์ชันได้ ถ้าทั้งสองยังไม่ถึงวัน
3. **แก้ได้เฉพาะก่อนถึงวัน**
   - เวอร์ชันที่ยังไม่มีผลเปลี่ยนบรรทัดได้
   - เวอร์ชันที่มีผลอยู่หรือผ่านไปแล้วไม่เปลี่ยน (`RECIPE_VERSION_IN_EFFECT`) ให้เพิ่มเวอร์ชันใหม่ที่เริ่มวันหลังแทน
   - ราคาใช้กติกาเดียวกัน ตั้งราคาซ้ำสำหรับรายการเมนู สาขา (หรือราคากลาง) และวันเดิม คือการแก้ ซึ่งทำได้จนกว่าจะถึงวันนั้น หลังจากนั้นระบบปฏิเสธ
     (`PRICE_IN_EFFECT`)
   - ราคาไม่มีวันเริ่มในอดีต (`EFFECTIVE_FROM_IN_PAST`) เพราะ POS ขายด้วยราคาของวันที่ผ่านไปแล้ว
   - ไม่มีอะไรในเมนูถูกลบ รายการเมนู กลุ่ม และตัวเลือกใช้การปิดใช้ และฐานข้อมูลปฏิเสธการลบ
4. **ราคาของสาขาชนะที่สาขานั้นตราบที่ยังมีผล**
   - ในแต่ละวัน สาขาคิดราคาของตัวเองที่มีผลวันนั้นถ้ามี ไม่มีจึงใช้ราคากลางที่มีผลวันนั้น
   - ราคากลางที่เปลี่ยนทีหลังไม่ทับราคาสาขาที่ยังมีผล
   - ราคาคือราคาขายตามที่ POS แสดง ภาษีเป็นเรื่องของ POS
5. **สูตรของตัวเลือกเป็นต่อหนึ่งหน่วยที่ขายในบรรทัดที่ตัวเลือกนั้นอยู่** และหักวัตถุดิบออกได้ (ปริมาณติดลบ เช่น "ไม่รับน้ำจิ้ม")
   การใช้ตามทฤษฎีของบรรทัดขายหนึ่งบรรทัดคือ
   - สูตรเมนู × ปริมาณของบรรทัด (หรือ `weightKg`) บวกกับ
   - สูตรของตัวเลือก × ปริมาณของตัวเลือก × ปริมาณของบรรทัด (หรือ `weightKg`) ของทุกตัวเลือก

   เป็นฟังก์ชัน domain ล้วน (`theoreticalUsage`) ตามที่สัญญา 1.0 ตกลงกับ POS เรื่องปริมาณตัวเลือกไว้แล้ว สูตรเมนูของรายการที่ขายตามน้ำหนัก
   เป็นต่อกิโลกรัมที่ขาย และวิธีขายของรายการเมนูเปลี่ยนไม่ได้หลังสร้าง
6. **ต้นทุนตามทฤษฎีของสูตรเป็นค่าประมาณ และแสดงว่าเป็นค่าประมาณ**
   - แต่ละบรรทัดคิดด้วย**ต้นทุน lot ปัจจุบัน**ของวัตถุดิบ คือต้นทุนต่อหน่วยของ lot ที่ FEFO จะใช้ถัดไป ได้แก่ lot ที่ยังไม่หมดอายุ
     มีของเหลืออยู่ที่ใดก็ได้ และหมดอายุก่อน ถ้าเท่ากันใช้ lot ที่เก่ากว่า
   - วัตถุดิบที่ไม่มี lot แบบนั้นถือว่าไม่มีต้นทุน ไม่คิดเป็นศูนย์ ยอดรวมจึงระบุว่าเป็น "อย่างน้อย" หรือ "ยังคิดต้นทุนไม่ได้" ถ้าไม่มีบรรทัดไหนมีต้นทุน
   - การตัดใช้จริงยังใช้ต้นทุนของ lot ที่ FEFO เลือก ณ สถานที่และเวลานั้น (ADR-0004) ไม่มีการลงบัญชีด้วยต้นทุนนี้
7. **การอ่านเมนูต้องมีสิทธิ์ `menu:read`** (admin, finance, branch manager) และเฉพาะ `menu:manage` (admin) แก้ได้
   - สูตรและต้นทุนเป็นข้อมูลทางการค้า ต่างจากสินค้าและสถานที่ที่ทุกคนที่เข้าสู่ระบบอ่านได้
   - finance ดูต้นทุน (ADR-0008) และ branch manager บริหารสาขาที่ขายเมนูนี้

## ผลที่ตามมา

- #17 แปลงยอดขายด้วย `recipeInEffect` ตามวันที่ทางธุรกิจของการขาย และ `theoreticalUsage` โดยไม่ต้องถามว่าเวอร์ชันถูกแก้หลังการขาย
  หรือไม่ เพราะแก้ไม่ได้
- สัญญา 1.1 บอก POS ได้ว่าราคาหรือสูตรที่เริ่มแล้วไม่เปลี่ยนอีก การแก้ราคาหรือสูตรล่วงหน้ามาเป็น `id` เดิมพร้อม `action: updated`
- สูตรที่พิมพ์ผิดและมีผลไปแล้วจะมีผลต่อจนกว่าเวอร์ชันของพรุ่งนี้จะเริ่ม ยอมรับข้อนี้ เพราะทางเลือกอื่นคือการเปลี่ยนการใช้ที่รายงานไปแล้ว
- demo seed เขียนราคาและสูตรของเมื่อวานลงฐานข้อมูลตรงๆ เพราะสคริปต์เขียนประวัติได้ ส่วน API ไม่ย้อนหลังเลย

## ทางเลือกที่พิจารณาแล้ว

- **เวอร์ชันที่มีวันสิ้นสุดชัดเจน** ไม่เลือก เพราะวันสิ้นสุดต้องคอยปรับให้ตรงกับวันเริ่มของเวอร์ชันถัดไป ช่องว่างหรือการซ้อนกันระหว่างสองค่านี้
  จะเป็นอีกช่องทางให้ผิด
- **ให้เวอร์ชันใหม่เริ่มวันนี้ได้** ไม่เลือก เพราะยอดขายที่แปลงไปแล้ววันนี้จะไม่ตรงกับสูตรที่วันเดียวกันใช้รายงาน
- **ใช้ต้นทุนเฉลี่ยถ่วงน้ำหนักของ lot ทั้งหมดที่มี** ไม่เลือกใน v1 เพราะเป็นต้นทุนที่บัญชีสต๊อกไม่เคยลง lot ถัดไปของ FEFO คือต้นทุนที่การขาย
  ครั้งถัดไปน่าจะใช้มากที่สุด และตรวจด้วยมือกับสต๊อกคงเหลือได้
- **เปิดเมนูให้ทุกคนที่เข้าสู่ระบบอ่านได้เหมือนสินค้า** ไม่เลือก เพราะสูตรและต้นทุนคือสิ่งที่คู่แข่งอยากเห็นที่สุด และบทบาท plant กับ purchasing
  ไม่จำเป็นต้องใช้
