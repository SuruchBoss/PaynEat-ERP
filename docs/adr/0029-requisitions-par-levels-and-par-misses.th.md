# ADR-0029: ใบขอเบิก: สถานะการส่งเดินตามของที่ใบโอนส่งออกไปจริง ค่าแนะนำเป็นจำนวนเต็มของหน่วยขอเบิก และนับการขาดของสองแบบ

- **สถานะ:** Accepted
- **วันที่:** 2026-10-10
- **English:** [0029-requisitions-par-levels-and-par-misses.md](0029-requisitions-par-levels-and-par-misses.md)

## บริบท

ADR-0009 ตัดสินว่าสาขาดึงของจากโรงงานด้วยใบขอเบิก หน้าจอแนะนำจำนวนจากระดับสต๊อกมาตรฐาน (par level)
และต้องมองเห็นการขาดของ (par miss) เพื่อให้ระดับสต๊อกมาตรฐานที่ตั้งไม่ดีโผล่ออกมา ADR-0028 ตัดสินว่าใบโอนย้ายของอย่างไร
ตอนสร้างใบขอเบิก (#15) ยังมีคำถามที่สองข้อนั้นไม่ได้ตอบ:

- ใบขอเบิกหนึ่งใบถูกส่งด้วยใบโอนหนึ่งใบหรือหลายใบ "ส่งมาบางส่วน" เป็นสิ่งที่ใบขอเบิกเก็บไว้เองหรือไม่
  และถ้าใบโอนถูกยกเลิกหรือการส่งถูกกลับรายการจะเกิดอะไรขึ้น
- โรงงานแพ็กไก่เป็นถาด สาขาขอ 18 ชิ้นหรือสองถาด
- การขาดของนับอะไรกันแน่ ในเมื่อธงยอดสาขาติดลบของ #8 เป็นการอ่านสต๊อกคงเหลือ ไม่ได้บันทึกว่ายอดติดลบเมื่อไหร่
- คนฝ่ายขนส่งสองคนอาจเตรียมใบโอนจากใบขอเบิกใบเดียวกันพร้อมกัน และสาขาอาจยกเลิกระหว่างนั้น
- #15 ขอให้ผู้จัดการสาขาทำได้เฉพาะสาขาของตัวเอง แต่ ERP ยังไม่รู้ว่าใครอยู่สาขาไหน

## การตัดสินใจ

1. **ใบขอเบิกเก็บสถานะเองแค่ ร่าง ส่งแล้ว หรือยกเลิก** "ส่งมาบางส่วน" กับ "ได้ครบแล้ว" อ่านจากใบโอนที่สร้างจากใบนั้น
   ไม่เก็บไว้: ใบที่ส่งแล้วจะเป็น "ส่งมาบางส่วน" เมื่อมีของส่งออกไปตามใบนั้นแล้ว และ "ได้ครบแล้ว" เมื่อทุกบรรทัดส่งไปถึงจำนวนที่ขอ
   นับเฉพาะของที่ใบโอนที่ส่งแล้วเอาออกจากโรงงานจริง: ร่างใบโอนเป็นแค่แผน ยังไม่นับ ใบโอนที่ยกเลิกเหมือนไม่เคยมี
   และการส่งที่ถูกกลับรายการ (ADR-0028 ข้อ 9) ไม่ได้ย้ายอะไร ใบขอเบิกจึงกลับไปสถานะเดิม ใบขอเบิกไม่เขียนสต๊อก
2. **ค่าแนะนำเป็นฟังก์ชัน domain ล้วน** `max(0, ระดับสต๊อกมาตรฐาน − ยอดที่สาขา − จำนวนที่กำลังมาส่งที่สาขา)`
   ปัดขึ้นเป็นจำนวนเต็มของหน่วยขอเบิกของสินค้าถ้ามี ยอดที่สาขาคือยอดของสินค้านั้นทุก lot รวมกัน และติดลบได้ (ADR-0003):
   ยอดติดลบทำให้แนะนำมากขึ้น เพราะของขาดจริง ที่กำลังมาส่งคือของที่ใบโอนที่ส่งไปสาขานั้นเอาออกจากต้นทางแล้ว ยังไม่รับเข้าและไม่ถูกกลับรายการ
   ทุกบรรทัดเก็บค่าแนะนำ ณ ตอนบันทึกบรรทัดไว้คู่กับที่คนขอจริง ไม่มีการคำนวณใหม่ทีหลัง
3. **หน่วยขอเบิกเป็นค่าตั้งของสินค้า** สินค้าตั้งได้ว่าโรงงานแพ็กส่งด้วยกันทีละกี่หน่วยนับ (ถาดละ 10 ชิ้น ถุงละ 2.5 กก.)
   เป็นค่าที่ผู้ดูแลระบบตั้งเหมือนเกณฑ์ตอนรับของ ไม่ใช่ master data ที่ POS ดึงไป และไม่ขึ้นเวอร์ชัน master data
   ใบขอเบิกต้องขอเป็นจำนวนเต็มของหน่วยขอเบิก ส่วนใบโอนไม่ถูกบังคับ เพราะฝ่ายขนส่งส่งเท่าที่มี
4. **ระดับสต๊อกมาตรฐานตั้งต่อสาขาต่อสินค้า** โดยผู้ดูแลระบบ (`par_level:manage`) ตั้งแต่ศูนย์ขึ้นไป ในหน่วยนับของสินค้า
   สินค้าที่ไม่มีจะไม่มีค่าแนะนำที่สาขานั้น แต่ยังขอเบิกได้
5. **ฝ่ายขนส่งส่งของด้วยใบโอนที่สร้างจากใบขอเบิก** ใบโอนแบบนี้ไปจากต้นทางของใบขอเบิกถึงสาขาของใบนั้นตลอดไป
   (service ปฏิเสธการเปลี่ยนเส้นทาง และฐานข้อมูลไม่ยอมเก็บ) มีได้เฉพาะสินค้าที่ใบขอเบิกขอ และเติมจำนวนที่ยังค้างให้:
   ที่ขอลบที่ส่งแล้วลบที่ร่างใบโอนวางแผนไว้แล้ว ไม่ต่ำกว่าศูนย์ ฝ่ายขนส่งส่งมากหรือน้อยกว่านั้นได้
   การสร้างใบโอนล็อกใบขอเบิกในทรานแซกชันเดียวกันและเลื่อน revision ของใบขอเบิก ถ้าสองคนเตรียมใบโอนพร้อมกัน
   คนที่สองจะถูกขอให้โหลดใหม่ แทนที่จะส่งจำนวนที่ค้างซ้ำสองรอบ
6. **ยกเลิกใบขอเบิกได้เฉพาะก่อนมีของส่งออกไปตามใบนั้น** พร้อมเหตุผล ร่างใบโอนของใบนั้นต้องให้ฝ่ายขนส่งยกเลิกก่อน
   เมื่อการส่งถูกกลับรายการ ใบขอเบิกก็ยกเลิกได้อีก การยกเลิกกับการสร้างใบโอนต่อคิวกันที่แถวของใบขอเบิก ทำให้ชนะได้ทางเดียว
   และฐานข้อมูลไม่ยอมให้ยกเลิกระหว่างที่มีใบโอนของใบนั้นเป็นร่างหรือส่งแล้ว
7. **ต้นทางค่าเริ่มต้นคือโรงงาน**: ถ้าไม่ระบุ ใช้โรงงานที่ใช้งานอยู่แห่งเดียวของบริษัท ถ้ามีมากกว่าหนึ่งต้องระบุโรงงานหรือคลังเอง
8. **นับการขาดของสองแบบ ต่อสาขาต่อสินค้า ในช่วงวันที่ทางธุรกิจ** (ค่าเริ่มต้นสี่สัปดาห์ถึงวันนี้):
   - **ยอดติดลบ:** เล่นยอดของสินค้าที่สาขา ทุก lot รวมกัน ทีละเอกสารตามเวลาทางธุรกิจ และในวันเดียวกันตามลำดับที่ post
     ทุกครั้งที่ยอดเปลี่ยนจากศูนย์หรือมากกว่าเป็นติดลบภายในช่วงนับหนึ่งครั้ง นี่คือการอ่านธงของ #8 ระดับสินค้า
     ธงนั้นไม่ได้ถูกเก็บไว้ จึงคำนวณจาก ledger แทนประวัติธงที่ไม่มีอยู่จริง
   - **ส่งไม่ครบตามกำหนด:** บรรทัดของใบขอเบิกที่ส่งแล้ว ซึ่งวันที่ต้องการอยู่ในช่วงและผ่านไปแล้ว และใบโอนที่ลงวันที่ไม่เกินวันนั้น
     และไม่ถูกกลับรายการ ส่งไปน้อยกว่าที่ขอ ใบขอเบิกที่เป็นร่างหรือยกเลิกไม่นับว่าขาด

   รายงานแสดงทุกสาขาและสินค้าที่มีระดับสต๊อกมาตรฐาน แม้ไม่เคยขาด เพื่อให้เห็นว่าค่าที่ตั้งไว้ใช้ได้ด้วย
9. **#15 ตั้งใจยังไม่ผูกสาขา** เหมือนการรับโอนใน #14 ใครถือ `requisition:raise` (ผู้จัดการสาขา) ขอเบิกให้สาขาไหนก็ได้
   ทุกขั้นของสาขาผ่านการตรวจสาขาของใบขอเบิกจุดเดียวใน service layer ซึ่ง #71 จะเติมการตรวจว่าคนนั้นอยู่สาขาไหน
   และขอบเขตของ #71 รวมใบขอเบิกแล้ว นี่เป็นการเบี่ยงจากเกณฑ์ข้อ "`branch_manager` เฉพาะสาขาของตัวเอง" ของ #15
   ตามการตัดสินของ product owner

## ผลที่ตามมา

- สถานะของใบขอเบิกไม่มีทางไม่ตรงกับใบโอน: ไม่มีอะไรต้องอัปเดตเมื่อใบโอนถูกยกเลิกหรือกลับรายการ
- ค่าแนะนำที่ผู้จัดการเห็นถูกบันทึกไว้คู่กับที่ขอจริง ระดับสต๊อกมาตรฐานที่ถูกแก้ทับเป็นประจำจึงเห็นได้ พอๆ กับตัวที่ขาดบ่อย
- ถาดเป็นค่าตั้ง ไม่ใช่หน่วยนับ: สต๊อก ต้นทุน และใบโอนยังเป็นหน่วยนับของสินค้า (ADR-0005)
- รายงานการขาดของเล่นรายการของสาขาใหม่ทุกครั้งที่เปิด ขนาดร้านอาหารเครือหนึ่งใช้ได้สบาย
  ถ้าต้องดูช่วงยาวหลายปีจะต้องเก็บประวัติธงไว้
- จนกว่า #71 จะเสร็จ console แสดงทุกสาขาให้ผู้จัดการสาขาทุกคน และ API รับใบขอเบิกของเขาให้สาขาไหนก็ได้
