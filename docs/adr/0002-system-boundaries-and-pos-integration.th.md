# ADR-0002: การแบ่งขอบเขตระบบและการเชื่อมต่อกับ PaynEat POS

- **สถานะ:** ยอมรับแล้ว
- **วันที่:** 2026-09-25
- **English:** [0002-system-boundaries-and-pos-integration.md](0002-system-boundaries-and-pos-integration.md)

## บริบท

PaynEat POS มีอยู่แล้วเป็น repository ของตัวเอง มีระบบจัดการเมนู วัตถุดิบ และสต๊อกของตัวเอง และใช้งานได้จริงสำหรับ
ร้านอาหารร้านเดียวที่ไม่มี ERP เลย เครือร้านอาหารต้องการที่เดียวที่เป็นเจ้าของรายการสินค้า สูตร ซัพพลายเออร์ และสาขา
และต้องการให้ทุกยอดขายไปถึงที่นั้นได้อย่างเชื่อถือได้ แม้อินเทอร์เน็ตของสาขาจะหลุดไปหลายชั่วโมงก็ตาม

## การตัดสินใจ

### ระบบแยกกัน repository แยกกัน

PaynEat ERP อยู่ใน repository ของตัวเอง และทำงานเป็นเซอร์วิสของตัวเองบนฐานข้อมูล PostgreSQL ของตัวเองที่เซิร์ฟเวอร์
กลาง ERP ไม่อ่านหรือเขียนฐานข้อมูลของ POS เลย และ POS ก็ไม่อ่านหรือเขียนฐานข้อมูลของ ERP เลย ทั้งสองระบบสื่อสารกัน
ผ่าน API ที่มีเวอร์ชันและ schema ของ event ที่มีเวอร์ชันเท่านั้น

### ข้อมูลแต่ละประเภทมีระบบที่เป็นเจ้าของข้อมูลเพียงระบบเดียว

| ข้อมูล | ระบบที่เป็นเจ้าของข้อมูล | อีกระบบหนึ่ง |
|---|---|---|
| รายการสินค้า หน่วยนับ การแปลงหน่วย อายุการเก็บ | ERP | POS เก็บสำเนา (mirror) เฉพาะส่วนที่ต้องใช้ |
| รายการเมนู ราคา สูตรเมนู สูตรของตัวเลือกเสริม | ERP | POS เก็บสำเนา และเป็นแบบอ่านได้อย่างเดียวในโหมดเชื่อมต่อ ERP |
| ซัพพลายเออร์ | ERP | — |
| สาขา (ในฐานะสถานที่เก็บสต๊อก) | ERP | POS ได้รับรหัสระบุสาขา |
| ออเดอร์ การชำระเงิน กะ ใบกำกับภาษี | POS | ERP ได้รับเฉพาะ event ยอดขายเท่านั้น |
| ยอดคงเหลือสต๊อกของสาขา | ERP | POS เก็บสำเนาไว้เพียงเพื่อแสดงสถานะ "หมด" (sold out) |

### POS ยังทำงานได้โดยไม่ต้องมี ERP

POS instance ทำงานใน**โหมดใช้งานเดี่ยว**เป็นค่าเริ่มต้น เหมือนที่ทำงานอยู่ทุกวันนี้ทุกประการ การลงทะเบียนกับ ERP จะ
เปลี่ยนไปเป็น**โหมดเชื่อมต่อ ERP** ซึ่งหน้าจอเมนู สูตร และวัตถุดิบจะกลายเป็นสำเนาแบบอ่านได้อย่างเดียว ร้านที่ดาวน์โหลด
เฉพาะ POS ไม่เสียอะไรเลย

### ยอดขายไหลจาก POS → ERP ผ่าน outbox

- ภายใน transaction ของฐานข้อมูลเดียวกับที่บันทึกการขาย POS จะเขียน **event ยอดขาย** หนึ่งรายการต่อหนึ่งบรรทัดการขาย
  ลงในตาราง outbox ได้แก่ รายการเมนู จำนวน**หรือน้ำหนักที่ชั่ง** (POS ขายตามน้ำหนักได้อยู่แล้ว) ตัวเลือกเสริม
  (modifier) สาขา เวลา และ **idempotency key**
- ตัวส่งที่ทำงานเบื้องหลังจะทยอยส่งข้อมูลจาก outbox ไปยัง API ของ ERP พร้อมการลองส่งซ้ำ (retry) คิวออฟไลน์ที่ POS
  มีอยู่แล้วจะรองรับช่วงที่สาขาออฟไลน์
- ERP ประมวลผลแต่ละ idempotency key ครั้งเดียวพอดี (exactly once) และแปลงบรรทัดการขายเป็นการใช้ตามทฤษฎีโดยใช้
  สูตรเมนูและสูตรของตัวเลือกเสริม**ที่มีผลอยู่ ณ เวลาที่ขาย** การแตกสูตรเป็นวัตถุดิบ (recipe explosion) เกิดขึ้นที่เดียว
  คือ ERP เพื่อให้การคิดต้นทุนและการเปรียบเทียบการใช้ตามทฤษฎีกับการใช้จริงมีแหล่งข้อมูลเดียว
- POS จะไม่ปฏิเสธการขายเพราะเหตุผลเรื่องสต๊อกเลย ดู ADR-0003 เรื่องสต๊อกติดลบที่สาขา

### master data ไหลจาก ERP → POS ด้วยการดึงตามเวอร์ชัน

การเปลี่ยนแปลง master data ทุกครั้งจะเพิ่มเลขเวอร์ชัน POS instance จะขอรับการเปลี่ยนแปลงนับจากเวอร์ชันล่าสุดที่ตัวเอง
นำไปใช้แล้ว การใช้วิธีดึง (pull) แทนการผลัก (push) ทำให้ instance ที่ออฟไลน์ไปหนึ่งวันตามทันได้เองโดยไม่ต้องทำอะไรเพิ่ม

### ตัวตนของเครื่อง (machine identity)

POS instance แต่ละตัวลงทะเบียนไว้ใน ERP และได้รับข้อมูลรับรองประจำเครื่อง (machine credential) ของตัวเอง instance
หนึ่งตัวอาจให้บริการหลายสาขา (POS รองรับหลายสาขาอยู่แล้ว) โดย ERP เป็นผู้แจ้งว่า instance นั้นให้บริการรหัสสาขาใดบ้าง
ใน v1 บัญชีผู้ใช้ของแต่ละระบบยังแยกกัน ไม่มีการลงชื่อเข้าใช้ครั้งเดียว (single sign-on)

### สัญญา (contract) ถูกทดสอบทั้งสองฝั่ง

API และ schema ของ event เผยแพร่เป็นไฟล์ที่มีเวอร์ชัน ทั้งสอง repository รัน contract test กับไฟล์เหล่านี้ ดังนั้นการ
เปลี่ยนแปลงที่จะทำให้อีกฝั่งพังจะทำให้ CI ล้มเหลวที่ฝั่งที่เป็นผู้เปลี่ยน

## ผลที่ตามมา

- ชั้นการเชื่อมระบบเป็นสิ่งส่งมอบหลักในตัวเอง ไม่ใช่แค่โค้ดเชื่อม (glue): outbox, idempotency และการดึงตามเวอร์ชัน
  เป็นส่วนหนึ่งของสิ่งที่โปรเจกต์นี้ตั้งใจแสดงให้เห็น
- POS ต้องมีการเปลี่ยนแปลงของตัวเอง (outbox, โหมดเชื่อมต่อ ERP, หน้าจอ master data แบบอ่านได้อย่างเดียว) ซึ่งติดตาม
  เป็น issue ใน repository ของ POS และจะเข้ามาในสัปดาห์ที่ 4 ของรุ่นแรก หลังจากกำหนดสัญญาให้ตายตัวในสัปดาห์ที่ 1
- สต๊อกที่โรงงานแบบใกล้เคียงเวลาจริง (near-real-time) ขึ้นอยู่กับการทยอยส่งข้อมูลจาก outbox สาขาที่ออฟไลน์ไปหนึ่งวันจะ
  แสดงการใช้ที่ล้าหลังไปหนึ่งวันจนกว่าจะกลับมาเชื่อมต่อ ข้อนี้ยอมรับได้และมองเห็นได้

## ทางเลือกที่พิจารณา

- **repository เดียวและฐานข้อมูลเดียวสำหรับทั้ง POS และ ERP** ปฏิเสธโดยเจ้าของผลิตภัณฑ์ (product owner) เพื่อแสดง
  ขอบเขตการเชื่อมระบบที่แท้จริง ซึ่งเป็นวิธีที่ POS และ ERP ถูกติดตั้งใช้งานจริงในอุตสาหกรรม
- **ให้ POS เขียนลงฐานข้อมูลของ ERP โดยตรง** ปฏิเสธทันที: จะทำให้การแยกระบบไม่มีความหมาย และผูก schema ของทั้งสอง
  ระบบไว้ด้วยกันตลอดไป
- **อัปโหลดแบบ batch ตอนสิ้นวัน (สรุปในรูปแบบเดียวกับ Z-report)** ปฏิเสธ: โรงงานจะต้องวางแผนจากการใช้ของเมื่อวาน และ
  การอัปโหลดที่ล้มเหลวจะทำให้ข้อมูลหายไปทั้งวันในครั้งเดียว
- **ให้ POS แตกสูตรเองแล้วส่งปริมาณวัตถุดิบที่ใช้** ปฏิเสธ: การคิดต้นทุนจะขึ้นอยู่กับว่า POS แต่ละเครื่องบังเอิญถือสูตร
  เวอร์ชันไหนอยู่
