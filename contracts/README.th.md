# สัญญาเชื่อมต่อ PaynEat ERP ↔ PaynEat POS

**เวอร์ชัน 1.0.0** · English: [README.md](README.md)

โฟลเดอร์นี้คือสัญญาเชื่อมต่อระหว่าง PaynEat ERP กับ PaynEat POS (ADR-0002) และเป็นแหล่งความจริงเพียงแห่งเดียว:
ERP สร้างตามนี้ POS สร้างตามนี้ และ**ทั้งสอง repository ทดสอบกับไฟล์เหล่านี้ใน CI** ฝั่ง ERP ตรวจตัวอย่างทุกไฟล์ในนี้ และใช้
schema ของ event ยอดขายตรวจสิ่งที่ได้รับ ฝั่ง POS ตรวจ event ที่ตัวเองสร้างและคำตอบของ ERP ที่อ่าน

| ไฟล์ | คืออะไร |
|---|---|
| [`pos/v1/openapi.yaml`](pos/v1/openapi.yaml) | สาม endpoint ที่ POS เรียก พร้อมคำตอบและข้อผิดพลาด |
| [`pos/v1/sales-event.schema.json`](pos/v1/sales-event.schema.json) | **event ยอดขาย v1**: บรรทัดขายหนึ่งบรรทัดที่ชำระแล้ว POS → ERP |
| [`pos/v1/sales-event-receipt.schema.json`](pos/v1/sales-event-receipt.schema.json) | คำตอบของ ERP เมื่อเก็บ event แล้ว (ครั้งแรกหรือซ้ำ) |
| [`pos/v1/master-data-changes.schema.json`](pos/v1/master-data-changes.schema.json) | **รายการเปลี่ยนแปลง master data v1**: หนึ่งหน้าของรายการเปลี่ยนแปลงหลังเวอร์ชันหนึ่ง ERP → POS |
| [`pos/v1/pos-instance.schema.json`](pos/v1/pos-instance.schema.json) | POS instance นี้คือใคร และดูแลสาขาไหนบ้าง |
| [`pos/v1/error.schema.json`](pos/v1/error.schema.json) | ทุกการปฏิเสธ พร้อม `reason` ที่ POS ใช้ตัดสินใจ |
| [`pos/v1/examples/`](pos/v1/examples) | ตัวอย่างที่ถูกต้องของแต่ละไฟล์ และ event ยอดขายที่ผิด (`invalid/`) ซึ่งต้องถูกปฏิเสธ |

เนื้อหาด้านล่างเป็นส่วนหนึ่งของสัญญา: บอกว่า POS เรียกอะไร**เมื่อไร** และทำอะไรกับคำตอบแต่ละแบบ ticket ฝั่ง POS ที่สร้างบนสัญญานี้คือ
`25-erp-connected-mode`, `26-erp-sales-outbox` และ `28-erp-connect-from-config` ใน repository ของ PaynEat POS

## การเชื่อมต่อ POS instance

1. ผู้ดูแลระบบ ERP ลงทะเบียน instance ด้วยรหัส (เช่น `POS-SILOM-1` ตามรูปแบบรหัสกลาง `^[A-Z0-9][A-Z0-9-]{1,31}$`)
   ชื่อ และสาขาที่ดูแล ERP แสดง **machine credential ครั้งเดียว** (ขึ้นต้นด้วย `pnepos_`) เพิกถอนได้และออกใหม่ได้
   และทุกครั้งอยู่ในบันทึกการตรวจสอบของ ERP
2. ผู้ดูแลระบบ POS ใส่ที่อยู่ของ ERP และ credential แล้ว POS ต้องเก็บ credential เป็นความลับ: ไม่อยู่ใน log, ไม่ส่งกลับไปที่แอป,
   ไม่แสดงบนหน้าจอหลังบันทึก และไม่อยู่ในไฟล์ export
3. ทุกการเรียกส่ง `Authorization: Bearer <credential>` และ `x-request-id`
4. POS อ่าน `GET /api/v1/pos/instance` เพื่อรู้รหัสของตัวเอง (ซึ่ง event ยอดขายทุกตัวต้องระบุ) และสาขาที่ดูแล ตามรหัสสถานที่กลาง
   สาขาใน POS ที่รหัสไม่ตรงกับรายการนี้ขายในโหมดเชื่อมต่อไม่ได้

ถ้าได้ `401` พร้อม `POS_CREDENTIAL_REJECTED` จากการเรียกใดก็ตาม แปลว่า credential ถูกเพิกถอน (`credential_revoked`)
หรือไม่เคยมีอยู่ (`credential_unknown`) การลองใหม่ไม่ช่วยอะไร POS ต้องหยุดเรียก ERP เก็บยอดขายที่รอส่งไว้ทั้งหมด และแจ้งผู้ดูแลระบบ
แล้วส่งต่อเมื่อบันทึก credential ใหม่ ERP เองก็ log และนับทุกการปฏิเสธแบบนี้ ผู้สืบสวนของเชนจึงเห็นด้วย

## master data: ดึงตามเวอร์ชัน

- master data ไหลทางเดียวจาก ERP → POS ในสัญญา 1.0 มี**สินค้า** (POS เก็บเป็นวัตถุดิบ จับคู่ด้วย `itemCode`) และ**สาขา**
  (จับคู่ด้วย `locationCode`) ส่วนเมนู ราคา ตัวเลือก และสูตร มาในสัญญา 1.1 (ERP #16)
- ทุกการเปลี่ยนแปลงได้เวอร์ชันถัดไปของทั้งบริษัท และ commit ตามลำดับ ผู้อ่านจะไม่เห็นเวอร์ชัน N+1 ก่อน N
- POS เก็บเวอร์ชันล่าสุดที่นำไปใช้แล้ว (เป็น 0 ก่อนดึงครั้งแรก) แล้วเรียก `GET /api/v1/master-data/changes?since=<เวอร์ชันนั้น>`
  นำหน้านั้นไปใช้**ตามลำดับเวอร์ชัน** เก็บเวอร์ชันสุดท้ายที่ใช้แล้ว และเรียกต่อตราบที่ `hasMore` เป็น true
  ดึงเป็นรอบตามเวลา และดึงทันทีเมื่อมีคนกด instance ที่ออฟไลน์ไปทั้งวันก็แค่ดึงตามให้ทัน
- `data` คือทั้งระเบียนหลังการเปลี่ยนแปลง: เขียนทับ mirror ไปเลย ไม่ต้องผสาน
- ไม่มีอะไรถูกลบ สินค้าหรือสาขาที่เลิกใช้จะมาพร้อม `active: false`
- สาขาที่รหัสผิดหลังถูกใช้งานไปแล้วจะถูก**แทนที่** (superseded): มาในสถานะปิดใช้งาน พร้อม `supersededBy` ที่บอกสาขาที่มาแทน
  POS ย้ายสาขานั้นไปใช้รหัสใหม่ โดยประวัติการขายไม่หาย
- **รองรับเวอร์ชันถัดไป**: POS ข้าม `entityType` ที่ไม่รู้จัก และไม่สนใจ field ที่ไม่รู้จัก สัญญา 1.x มีแต่การเพิ่มสองอย่างนี้
  POS ที่เขียนตาม 1.0 จึงยังใช้กับ 1.1 ได้
- การดึงที่สำเร็จแต่ละครั้งคือ "การดึงล่าสุด" ของ instance ใน ERP ผู้สืบสวนของเชนดู
  `erp_master_data_last_pull_timestamp_seconds{pos_instance}` เพื่อหา POS ที่หยุดดึง

## event ยอดขาย: outbox และส่งถึงครั้งเดียวแน่นอน

**event ยอดขายเกิดเมื่อไร**: เมื่อ**บรรทัดขายได้รับชำระ** (บิลของบรรทัดนั้นชำระครบ หรือมีการชำระที่ครอบคลุมบรรทัดนั้น เช่นตอนแยกบิล)
POS สร้าง event หนึ่งตัวให้บรรทัดนั้น ถ้าไม่ถูกยกเลิก

- `saleTime` คือเวลาของการชำระนั้น พร้อม UTC offset
- บรรทัดที่ขายเป็นจำนวนใส่ `quantity` บรรทัดที่ขายตามน้ำหนักใส่ `weightKg` เป็นน้ำหนักจริงที่ขาย หน่วยกิโลกรัม
  ห้ามใส่ทั้งสองอย่าง
- `menuItemCode` และ `code` ของตัวเลือกแต่ละตัวคือรหัสของ ERP (ได้มาพร้อมสัญญา 1.1) เมนูที่ยังไม่มีรหัส ERP ขายในโหมดเชื่อมต่อไม่ได้
  จึงไม่มีบรรทัดที่ไม่มีรหัส
- ส่งตัวเลือกไปด้วย `quantity` ของตัวเลือกคือจำนวน**ต่อหนึ่งหน่วยที่ขายในบรรทัด**: ต่อชิ้นเมื่อบรรทัดใช้ `quantity` ต่อกิโลกรัมเมื่อใช้
  `weightKg` วัตถุดิบที่ใช้ = สูตรของตัวเลือก × `quantity` ของตัวเลือก × `quantity` (หรือ `weightKg`) ของบรรทัด
- **ยังไม่ส่งใน v1**: การคืนเงินหรือ void หลังชำระ และอาหารที่ทำแล้วแต่ถูกยกเลิกก่อนชำระ ส่วนต่างนี้ให้การตรวจนับสต๊อกเป็นตัวจับ
  (`docs/DECISIONS.md` #66 ของ PaynEat POS) จึงไม่มี event ที่จำนวนเป็นศูนย์หรือติดลบ

**outbox**: POS เขียน event แต่ละตัวลงตาราง outbox **ใน transaction เดียวกับการชำระเงิน** ถ้าการชำระล้ม ก็ไม่มี event
ถ้าสำเร็จ event ก็หายไม่ได้ POS ในโหมดใช้งานเดี่ยวไม่เขียนอะไรเลย

**idempotency key** ระบุบรรทัดขายนั้น: คงที่ทุกครั้งที่ลองส่งใหม่ และไม่ซ้ำกันทั้งเชน **key ต้องไม่ซ้ำแม้ติดตั้งฐานข้อมูล POS ใหม่**
จึงมี id ของฐานข้อมูลรวมอยู่ด้วยนอกจาก order item: `<pos-instance>-<id ฐานข้อมูล 6 ตัว>-<id ของ order item 8 หลัก>` เช่น
`POS-SILOM-1-K3F9Q2-00001234` (ยาวไม่เกิน 48 ตัวอักษร) key นี้เป็น **correlation id** ของ event ด้วย (docs/TELEMETRY.md) จึงส่งเป็น `x-request-id`
ทุกครั้งที่ส่ง และต้องใช้เฉพาะตัวอักษรที่ header นั้นรับ: `^[A-Za-z0-9_-]{8,64}$` ซึ่งไม่มีเครื่องหมาย `:` จึงใช้ `-` คั่นแทน
ไม่มี id ตัวที่สอง: บรรทัด log ของ ERP เรื่อง event นี้ บรรทัดของ POS เรื่องการส่ง และการสืบสวนจาก metric ทั้งสองฝั่ง ตามค่านี้ค่าเดียว

**การส่ง**: ตัวส่งเบื้องหลังส่งจาก outbox ตามลำดับ หนึ่ง event ต่อ `POST /api/v1/sales-events` และทำตามคำตอบ:

| คำตอบ | ความหมาย | POS ทำอะไร |
|---|---|---|
| `201` | เก็บแล้ว | ทำเครื่องหมายว่าส่งแล้ว |
| `200` พร้อม `duplicate: true` | เคยเก็บแล้ว (ครั้งก่อนส่งถึง) ไม่มีการเก็บซ้ำ | ทำเครื่องหมายว่าส่งแล้ว |
| `422` `SALES_EVENT_REJECTED` | จะไม่มีวันรับได้ในรูปนี้ `details.reason` บอกเหตุผล ERP ไม่ได้เก็บอะไร | ย้ายไป dead letter พร้อมเหตุผล ให้คนมาดู |
| `401` `POS_CREDENTIAL_REJECTED` | credential ถูกเพิกถอนหรือไม่มีอยู่ | หยุดทั้งคิว เก็บทุกแถวที่รอส่งไว้ตามเดิม และแจ้งผู้ดูแลระบบ ส่งต่อเมื่อบันทึก credential ใหม่ |
| `429` | ที่อยู่นี้เรียกถี่เกินไป | รอตาม `Retry-After` วินาที แล้วลองใหม่ |
| `5xx`, หมดเวลา, ไม่มีเน็ต | ERP ตอบไม่ได้ | ลองใหม่ไปเรื่อยๆ แบบ exponential backoff ที่มีเพดาน (POS ตั้งเพดานไว้ 5 นาที) ด้วย key เดิมทุกครั้ง ถ้าได้ `503` พร้อม `Retry-After` ให้รอตามนั้น ไม่ย้ายไป dead letter: `outbox_oldest_pending_age_seconds` เป็นตัวเตือน |
| สถานะอื่นใด (`400`, `403`, `404`, `405`, `413`…) หรือ `2xx` ที่ body ไม่ใช่ใบรับที่ถูกต้อง | ตั้งค่าผิด: ที่อยู่ผิด มี proxy คั่น หรือเวอร์ชันสัญญาไม่ตรงกัน | เหมือน `401`: หยุดทั้งคิว เก็บทุกแถวที่รอส่งไว้ตามเดิม และแจ้งผู้ดูแลระบบ ไม่ย้ายไป dead letter ส่งต่อเมื่อบันทึกที่อยู่หรือ credential ใหม่ |

**dead letter มาจาก `422` เท่านั้น** การถูกปฏิเสธไม่ทำให้ key ถูกใช้ไป: `422` ไม่เก็บอะไรเลย เมื่อแก้สาเหตุแล้ว (เช่น instance
ดูแลสาขานั้นแล้ว) event เดิมที่ส่งซ้ำจาก dead letter ด้วย key เดิมจะถูกรับเป็นของใหม่ (`201`) ยกเว้น `idempotency_key_reused`
ซึ่ง key นั้นเป็นของบรรทัดขายอื่นไปแล้ว

**ERP เก็บแต่ละ idempotency key ครั้งเดียวแน่นอน** แม้ event เดียวกันจะมาพร้อมกันหลายครั้ง ERP ตรวจตามลำดับนี้:

1. credential (`credential_revoked`, `credential_unknown`)
2. schema (`schema_invalid` พร้อม `details.errors`)
3. `posInstance` ต้องเป็น instance ของ credential นั้นเอง (`pos_instance_mismatch`)
4. สาขาต้องเป็นสาขาที่ instance ดูแล (`branch_not_served`)
5. key ที่เคยเห็นแล้วต้องมากับ event เดิม (ถ้าไม่ใช่เป็น `idempotency_key_reused`: ห้ามใช้ key ซ้ำกับบรรทัดขายอื่น)

event ที่เก็บแล้วอยู่ในสถานะ `received` การแปลงเป็นการใช้วัตถุดิบตามสูตรที่มีผล ณ `saleTime` เป็นงานของ ERP ตั้งแต่ ERP #17
POS ไม่ต้องรอ และการขายไม่ถูกปฏิเสธเพราะสต๊อก

## Telemetry

ทั้งสองฝั่งทำตาม [docs/TELEMETRY.md](../docs/TELEMETRY.md) v1.2 หัวข้อ "POS↔ERP integration lines" ทุกบรรทัด log
เรื่องการเชื่อมต่อนี้มี `pos_instance` และถ้าเกี่ยวกับสาขาเดียวก็มี `location_code` ด้วย รวมบรรทัดที่ล้มเหลว
จะเว้น label ได้ก็ต่อเมื่อรู้ค่าไม่ได้จริงๆ และห้ามเดาค่า

ERP เขียนและนับ:

| สัญญาณ | คืออะไร |
|---|---|
| `sales_event.received` / `sales_event.duplicate` | บรรทัดเรื่อง event ที่เก็บแล้ว `correlation_id` คือ idempotency key |
| `sales_event.rejected` | event ที่ถูกปฏิเสธ พร้อม `reason` |
| `erp_sales_events_total{outcome, reason}` | ทุก event แยกตามผล |
| `master_data.pulled` | การดึงที่สำเร็จ |
| `master_data.pull_refused` | การดึงที่ถูกปฏิเสธ พร้อม `reason` |
| `erp_master_data_last_pull_timestamp_seconds{pos_instance}` | การดึงที่สำเร็จล่าสุดของแต่ละ instance อ่านจากฐานข้อมูล |

ฝั่ง POS เขียน `outbox.delivery.failed` และ gauge `outbox_*` ตัวที่บอกว่ายอดขายค้างรอเพราะติดต่อ ERP ไม่ได้คือ
`outbox_oldest_pending_age_seconds`

## เวอร์ชัน

สัญญามีเวอร์ชันแบบ semver ซึ่ง `GET /api/v1/pos/instance` ส่งมาเป็น `contractVersion`:

- **minor** (1.0 → 1.1): มีแต่การเพิ่ม endpoint, field ที่ไม่บังคับ, ชนิดข้อมูล หรือค่า enum ที่ฝั่งรับข้ามได้
- **major** (2.0): การเปลี่ยนแปลงแบบอื่นทั้งหมด ได้โฟลเดอร์ `pos/v2/` ของตัวเอง และ ERP รองรับทั้งสองเวอร์ชันจนกว่า POS ทุกเครื่องจะย้ายแล้ว

ทุกการเปลี่ยนแปลงบันทึกใน [CHANGELOG.md](CHANGELOG.md) การแก้ไขอะไรก็ตามในโฟลเดอร์นี้ต้องให้ product owner ตรวจก่อน merge
